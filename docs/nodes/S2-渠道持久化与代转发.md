> 状态：任务书 v1，待双路审计

> 验收形态红线（适配包 §红线7-9）：交付=成品+验收入口+测试账号；说明与界面逐条一致

## 一、目标（需求四问）

① 谁用：注册登录后的画布用户——在配置页录入自己的渠道 key，换设备/换浏览器登录后配置还在。
② 痛点卡在哪：现在渠道配置存浏览器 localStorage，换设备即丢、清缓存即丢。
③ 做成的判据：换设备登录→渠道配置完整出现；盘上/接口零明文 key；生成请求走服务端代转发成功。
④ 与现状关系：替代「localStorage 持久化」这一步，store 结构与 action 签名不动。

## 二、改点清单

### B1 后端：渠道存储 + 加密（wanrepro/ui/）
1. 新模块 `channel_store.py`：SQLite 表 `user_channels(user_id, name, base_url, api_key_enc, api_format, models_json, updated_at)`；WAL+busy_timeout+foreign_keys=ON（沿用 multiuser 惯例）。
2. AES-GCM 加密（`cryptography` 库）：主密钥从 env `WANREPRO_CHANNEL_KEY`（base64 32 字节）读取；缺失时启动 FAIL 并明文报错（零兜底，不静默降级为明文存储）；密文格式 `[1字节版本][12B nonce][ciphertext+16B tag]`；读接口零回显（GET channels 返回 masked `sk-***last4`）。
3. CRUD 路由：`GET/PUT/DELETE /api/user/channels`（登录态必需，未登录 401）；`PUT` 全量替换该用户渠道集（与前端 store 整体保存语义对齐）。**masked 回写护栏（审计 BL-1）**：PUT 时某渠道 `api_key` 匹配 masked 格式（`***` 结尾4位）→ 按 name+baseUrl 匹配保留原密文不覆盖；匹配不到 → 该渠道拒绝（422，报「请重新输入完整 API Key」）。
4. SSRF 校验：注册/更新渠道时校验 base_url——scheme 必须 https（http 仅允许 localhost/127.0.0.1 开发态）、解析 IP 拒绝 loopback/私网/link-local/保留段（含 IPv6）；每次代转发前重验。
5. 单人回归：`MULTI_USER=0` 时新路由全部 404、bootstrap-config 行为逐字节不变（行为等价判据）。

### B2 后端：代转发端点
1. `POST/GET /api/proxy/<channelId>/<path>`：登录态校验 → 查**该用户**渠道表（他人 channelId=404，不泄露存在性）→ 取 baseUrl 拼 path → 注入 `Authorization: Bearer <key>`（gemini 型渠道注入 `?key=`）→ 原样转发。方法白名单 POST/GET（审计 IF-4：模型列表拉取是 GET 语义）。
2. SSE 保真：不设 Content-Length、按块 read+write+flush、剥 hop-by-hop 头、客户端断连时关闭上游连接。
3. 防护：请求体上限、上游超时、单用户并发上限；禁重定向（3xx 原样透传不跟随）。
4. 日志只记 时间/方法/channelId/上游状态码/耗时；**不记 URL query、不记任何 key/Authorization**。

### B3 前端：persist 层改造（store 结构/action 签名不动）
1. `use-config-store.ts`：`channelMode: "local"` 硬编码（L275/309）改为按登录态判定——已登录=`server`，未登录保持 `local`（单人模式零改动）。登录态来源约定：bootstrap 期先查 `/api/auth/me`（独立于 store 创建，避免循环依赖）。
2. persist 层：已登录时 channels 变更 → subscribe+debounce PUT `/api/user/channels`；beforeunload flush 未落盘变更；加载时 GET 覆盖本地缓存。
3. 一次性迁移（审计 BL-2 冲突规则定稿）：登录成功后先 GET——服务端渠道集**非空 → 丢弃本地缓存不迁移**（服务端为权威源）；服务端**为空 → 才执行本地→PUT 迁移**；迁移完成后本地键永久降级缓存。
4. 渲染门控：迁移/首次 GET 完成前，配置页不得以本地陈旧数据完成首次可交互渲染（loading 态挂起）。
5. 请求层 4 文件（image.ts/video.ts/audio.ts/model-plugin.ts）：服务端模式改发 channelId+模型名到 `/api/proxy/...`，bridge 注入 key；`isAiConfigReady` 的 key 非空检查按模式豁免；非渠道请求（image-storage/file-storage）不得误路由。

## 四、批次划分（生产者→消费者顺序）

| 批 | 内容 | 级别 | 依赖 |
|---|---|---|---|
| B1 | channel_store.py + AES-GCM + CRUD + SSRF 校验 + 单人回归 | M-L | 无（最先，生产者） |
| B2 | 代转发端点 + SSE | M | B1 |
| B3 | 前端 persist + 迁移 + 请求层 4 文件 | L | B1+B2 路由合同冻结 |
| B4 | 部署 :8780 + 双端验收 + 文档 | S | B3 |

依赖声明：B1 产出加密存储与渠道 CRUD 合同；B2 消费 B1 的解密读接口；B3 消费 B1/B2 的路由合同（路径/请求/响应 schema 冻结后才开工）。

## 五、边界（不做）

- 积分计费/平台统一渠道（B 阶段）
- 渠道密钥轮换 UI（密文带版本字段已预留，功能后置）
- Agent 多租户（一期砍掉）
- bootstrap 预置升级（方案 v2 line 68「管理员预置只下发非敏感元数据」）→ 本批不做，S3 或 S4 另立；:8780 现有 bootstrap-config 行为本批保持原样
- :8780 转 systemd（S2 部署批次顺手做，不算独立批）
