# S3.6 任务书 · 生成失败真实原因透传（节点错误卡片不吞上游状态）

> 状态：v1.0（2026-11-18 立卡待派）
> 上游拍板：2026-11-18 用户指令「把这些遗留问题用标准流程做收尾」
> 背景：2026-11-18 诊断链实证——用户画布生成失败时节点只显示「生成失败」，真实原因是聚鑫网关对 `/v1/responses` 协议返回 503 `channel:protocol_unsupported`（当日服务器侧直连实测拍板），但用户在界面上看不到任何上游信息，连续多轮盲试。根因修复（chat/completions，commit 92566dd）已落地，本卡治理「失败不可判因」这个独立缺陷。
> 基线：dev 分支 `92566dd`（chat/completions 修复已落地）。红线：单人模式零改动语义不破坏；零兜底（错误透传不做美化降级）；不可验收禁交。

## 一、问题定义（代码机制，2026-11-18 实测锚定）

上游真实信息在三处被折叠：

| # | 落点 | 机制 | 后果 |
|---|---|---|---|
| M1 | `web/src/services/api/image.ts:300` `readStatusError` | body 无 message 时按状态码映射通用 i18n 文案：503→「服务繁忙（503）」、429→「请求被限流或额度不足」、401→「鉴权失败…」 | 上游 new_api_error 原文（如「当前可用渠道无法处理该模型的此类协议请求」）不可见，用户无法区分协议不支持 vs 限流 vs key 失效 |
| M2 | `web/src/components/canvas/canvas-node.tsx:535/701/957` | `{errorDetails \|\| t("canvas.node.failed")}`，errorDetails 为 undefined 时兜底「生成失败」 | 上游信息即使拿到了，也可能因为 errorDetails 被清空而只显示兜底 |
| M3 | `web/src/pages/canvas/project.tsx:3956`（retry 路径 catch） | `errorDetails: item.metadata?.content ? undefined : errorDetails`——节点已有内容时**主动清空** errorDetails | 失败但保留旧内容的节点不显示任何失败原因 |

`responseErrorMessage`（image.ts:396）已能读出 new_api_error 的 `error.message`/`msg`——通道存在，问题只在 M1 兜底掩盖 + M2/M3 不落盘/被清。

## 二、目标

失败节点（含重试路径、含保留旧内容的节点）必须展示：**HTTP 状态码 + 上游 error 原文**。上游 body 无 message 时显示状态码+简短类别（既有 i18n 文案可用），**但状态码必须始终可见**——本次事故中「503」这一个数字就能让用户立刻转向协议排查。

不做：错误分类自动重试/自动换模型；上游文案 i18n 翻译（原文透传）；错误上报。

## 三、核心设计

1. **M1 改法**：`readFetchError`/`readStatusError` 的返回改为「状态码 + 上游原文（如有）拼接」，通用类别词保留为前缀（如「服务繁忙（503）：当前可用渠道无法处理…」），不再用通用文案**替代**上游原文。改法收敛在这两个函数，所有 request* 调用点（image.ts:531/557/664 等共用）自动受益。
2. **M2 改法**：失败态节点 errorDetails 为空时兜底行显示「生成失败（原因未捕获）」并 console.warn 带节点 id，使「原因丢失」本身可见可查——禁止静默兜底。
3. **M3 改法**：retry/主路径 catch 中，节点已有内容时**不清空** errorDetails——内容保留、失败原因并存（canvas-node.tsx 节点结构支持错误行与内容同时渲染，样式冲突时以「错误行可见」优先）。
4. 网络层错误（fetch reject：超时/断连，无上游响应）：保持 error.message 原文，不映射、不美化。
5. 单人/登录模式同一套逻辑（共用 requestImageQuestion，无分叉）。
