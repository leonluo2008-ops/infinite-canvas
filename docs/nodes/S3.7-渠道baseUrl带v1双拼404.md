# S3.7 任务书 · 渠道 baseUrl 含 /v1 时拉模型列表 /v1/v1 双拼 404

> 状态：v1.0（2026-11-18 立卡待派）
> 上游拍板：2026-11-18 用户指令「把这些遗留问题用标准流程做收尾」
> 背景：用户在 Ollama Cloud 渠道（baseUrl=`https://ollama.com/v1`，自带 /v1 后缀）下拉模型列表报错。当日实锤：前端 buildApiAbsoluteUrl 对不带 /v1 的 baseUrl 补 /v1，服务端 _forward 又拿渠道原始 base_url path（含用户填的 /v1）与 subpath 拼接 → 上游收到 `/v1/v1/models` → 404。临时解法（用户渠道地址去掉尾 /v1）已给，本卡根治。
> 基线：dev 分支 `92566dd`。红线：单人模式零改动语义不破坏；BYOK（用户已填渠道不做静默改写）；零兜底。

## 一、问题定义（代码机制，2026-11-18 实测锚定）

| # | 落点 | 机制 |
|---|---|---|
| F1 | `web/src/stores/use-config-store.ts:534` `buildApiAbsoluteUrl` | baseUrl（去尾斜杠后）不以 `/v1` 结尾则补 `/v1`，再拼 path（如 `/models`）→ 产物形如 `https://ollama.com/v1/v1/models`？否——**注意**：该函数只产「绝对 URL 形态的路径参考」，SaaS 登录模式实际走 channelApiUrl（`/api/proxy/<cid>/<path>`）；本地直连模式才用它的产物直连 |
| F2 | `wanrepro/ui/channel_store.py:663` `_forward` | `target = base.path.rstrip("/") + "/" + subpath.lstrip("/")`——base.path 是渠道原始 base_url 的路径部分。用户填 `https://ollama.com/v1` 时 base.path=`/v1`；而前端送的 subpath 已经是 `/v1/models`（F1 补过 /v1）→ 拼出 `/v1/v1/models` → 404 |

双拼只在「用户 baseUrl 自带 /v1」+「登录代转发模式」下发生（本地直连模式 F1 补 /v1 后 base.path 与补 /v1 的逻辑一致，不会双拼——本地直连最终 URL 只有一个 /v1）。

## 二、目标

用户渠道 baseUrl 无论带不带尾 `/v1`，登录代转发模式下拉模型列表、生成请求都打到正确的上游路径（只含一个 /v1）。**不改用户已存数据**（不静默改写用户 baseUrl），改拼接逻辑本身。

## 三、方案选项（实现前定案，倾向 B）

| 选项 | 做法 | 权衡 |
|---|---|---|
| A | 前端：channelApiUrl 的 path 侧对「/v1 开头的 subpath」去重（送 subpath 前剥一层 /v1）+ 服务端 `_forward` 拼接前对 target 做同样去重（防御双保险） | 前后端各一处、语义对称；服务端层兜住未来其他调用方 |
| B | 仅服务端 `_forward` 拼接后归一：`target` 中连续的 `/v1/v1` 折叠为 `/v1` | 改动最小（一行级）；但「语义上谁该补 /v1」的口径仍未收敛，前端直连与代理两条路径口径继续分叉 |

推荐 **A**（口径收敛在前端补 /v1 的唯一职责点 + 服务端防御），理由：双路径（直连/代理）共用同一 subpath 语义，只在服务端折叠会把口径留在模糊态，后续接入新调用方（如 workflow-instance-run）容易再踩。
