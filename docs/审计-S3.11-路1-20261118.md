## 三、必答追问：做完能否真跑通？（独立全链追踪）

链路实追：`use-plugin-host.tsx requestVideoGeneration` → `createVideoGenerationTask`(video.ts:92 wan 分流) → `createWanVideoTask`(:394, POST wanVideoUrl+/run, **confirm:true 即付费**) → `pollWanVideoTask`(:427, /job/→/file/) → blob。服务端 `route_post`(:2513-2545) → `do_wan_video_run`(:2941) → `wan_prepare_task`(:1016, 写 `ANALYSIS/<task>/提示词-*.md`) → 后台线程 `run_py(wan_argv…)` → `wan_video.py`（ROOT=parents[2] 自解析，ANALYSIS=ROOT/analysis/reverse，plan 不碰 CLI、submit 才进 `wan_submit.cli_prefix`）。

**a) 登录门/多用户路由：不会拦，但这是问题不是幸运。**
`route_get`(:2301-2311)/`route_post`(:2513-2521) 顺序：multiuser.handle → channel_store.handle → project_store.handle → **route_missing**（只认 `/api/auth/`、`/multiuser/`，multiuser.py:214-215）→ **login_guard**（:218-226，`path.startswith("/api/")` 直接 return False，**根本不管 API 路由**）→ 才到 wan 端点。`channel_store.handle` 只认领 `/api/user/channels` 与 `/api/proxy/`。所以 `/api/wan/video/*` 四端点在 MULTI_USER=1 下对**未登录请求完全敞开**——链路通（服务器实测 confirm=false 200 佐证），但构成 §一.4 的 BLOCKING 安全缺口。**结论：B1-4 的前端改动能通，但服务端必须同时补登录门，否则上线即裸奔付费引擎。**

**b) 哨兵对本地模式的带坏风险：分支基本干净，留一个 POLISH 护栏。**
本地（solo/未登录）模式渠道全部来自 localStorage，服务端渠道在 remote 模式明确不落 localStorage（对照表 §2），哨兵不会进入本地渠道集；本地自建 wan 渠道 baseUrl 仍是 `127.0.0.1:8779` 回环，wanVideoUrl 本地分支零改动。唯一残余路径：用户手工把服务端下发的哨兵渠道导进本地配置（config-file 导入/导出）。建议 POLISH：wanVideoUrl 对 `wan://` 开头的 baseUrl 也按同源处理（一行防御），不依赖模式判定。

**c) 工作目录/输出目录：不受 multiuser 影响，但有多用户共享语义问题。**
`server.py:47/82` ROOT/ANALYSIS 均由 `__file__` 派生（服务器 `/home/luo/wanrepro-s1-test/wanrepro` 自洽）；`wan_video.py:28-29` 同理由自身路径派生，与部署位解耦，multiuser 不改任何路径。**但**：`生成/` 目录与 `ANALYSIS/reverse/<task>` 是**全局共享**的——无 per-user 命名空间；`WAN_BUSY` 单并发位（:2971，CLI 只认一条）在多用户下是全站共享，第二个用户直接 409「已经有一个万相生成在跑」。单人 SaaS（当前形态）可接受，须在文档明示；多租户前必须改。

## 四、裁决点（必答）

**P1 成片下载：推荐 A+B（A 为默认，B 为兜底），不是纯 A。**
- 理由：受影响的「同 host、无凭据、路径不含 baseUrl 前缀」直链（/files/ 类 CDN）今天经代理**必 404**（695 行强拼 base.path），A 直连是纯收益、零服务端改动、与单机版一致。但纯 A 覆盖不了「同 host、无凭据、却要 Bearer 才能拉」的 content 端点型成片（openai 兼容渠道常见）：这类地址今天若 pathname 恰好带 /v1 前缀走代理**是好的**（服务端注 key），A 一刀切直连会丢凭据注入 → 401。所以 A 默认直连 + 直连失败（CORS/401/403）时带 `__abs=1` 回落代理（B），两层各取所长。
- 否决纯 A：上述 Bearer 场景必坏，且浏览器直连跨源 CDN 有 CORS 不确定面（方案 §六.4 自己也承认）。
- 否决纯 B：全部媒体过代理 = 服务端带宽/并发放大（PER_USER_CONCURRENCY=2 会被成片下载占坑），且新协议面全量启用，探针成本最高。
- 否决 C：方案已自证（破坏 S3.7 子路径合同、误伤 /v1/chat），同意否决。

**P2 哨兵形态：推荐 `wan://server-bridge`（方案原选），配「所有 https/URL 假设处显式豁免 wan」。**
- 理由：非 http(s) scheme 让任何「当普通 URL 用」的代码路径**快速显式失败**而不是静默拼错地址；`new URL()` 可解析（host=server-bridge），hostOf/stripBasePath 均安全；可 grep、语义自明。
- 否决空串：`isAiConfigReady`(:222) 与 `assertWanVideoConfig`(:387) 都要求 baseUrl 非空，空串直接判不就绪/抛错，还得改这两处语义，改动面更大。
- 否决 `http://127.0.0.1:8779`：对 SaaS 服务器是**谎言**（8779 不在那台机器的语义上），且 http 过不了 `_forward` https 检查、`isLocalOnlyChannel` https 正则，等于埋一个永远走不通的地址；单机回环值混进服务端表还会诱发「本地能连、服务器连不上」类幽灵排障。
- 附带条件：哨兵落库同时，前端 `isLocalOnlyChannel`(https 正则)、渠道页展示层、（若做 P3 降级）就绪判定都要点名豁免——B1-3 的遗漏就是没全列豁免点的实例。

**P3 未装 CLI 降级提示：推荐「降级为不可用提示」（有保留地否决方案的『彻底不显示』）。**
- 理由：A5 已证明未装 CLI 时建任务照样 200（假绿），若渠道彻底不显示，所有者装完 CLI 前连「差什么」都看不见；且「服务器没装 wan CLI」是**部署态**不是渠道配置错误，用户侧隐藏只会把排障成本转成工单。最小实现：`_view` 附一个 `wan_ready` 健康位（服务端启动时 `shutil.which("wan")` 一次），前端渠道卡显示但模型不就绪、徽标文案「服务器未装万相 CLI」。
- 否决「彻底不显示」：与 A4/A5 假绿叠加会造成「配了却不知道为什么不能用」；「单机版没有的概念不新增」原则适用于交互语义，不适用于部署健康度信号——这类信号是 SaaS 必要新增（SaaS 本身就是单机版没有的概念）。
- 保留意见：若所有者坚持极简，可接受「不显示」，但必须在 B2 未完成前于部署文档标注 wan 链不可用，避免误判回归。
