### 2. 探针用例 ③ 存在输入/期望不自洽（IMPL-FIXABLE，修文档再开工）：

方案 §三.3 ③ 写「baseUrl `…/openai/v1` + `/v1/models` → `/api/proxy/<cid>/models`」。按裁剪规则推演：若调用真是 `channelApiUrl(config, "/v1/models")`，`buildApiAbsoluteUrl` 得 `/openai/v1/v1/models`（baseUrl 已带 /v1 不再补，path 原样接上），剥 basePath `/openai/v1` 后剩 `v1/models` → 代理地址应为 `/api/proxy/<cid>/v1/models`，**不是** `/models`。③ 的本意显然是「② 的多段 basePath 版」，输入应为 `+ /models`（absolute `/openai/v1/models` → 剥 → `models` → `/api/proxy/<cid>/models`）。**照文实现断言必错。修正：③ 输入改为 `/models`，或期望改为 `/v1/models` 并注明该形态语义（调用方显式带了版本段的 path）。**

## 四、裁决点：服务端 `_forward` 要不要加「去重防御」？

**推荐：不加。**

理由：
1. **收益极小**：滚动窗口内旧 bundle 发 `/v1/v1/...` 的后果是 404——这正是**今天的现状**，加防御没有修复任何新回归，只是让「本来就坏的 Ollama 渠道」在窗口内顺带变好。为一个已知的、自愈的（bundle 换名 + 刷新即载新）窗口引入永久性双合同，不划算。
2. **误判风险真实存在**。若按「subpath 以 base.path 最后一段开头则剥一层」实现：
   - gemini 渠道 baseUrl `https://host/v1beta`（合规形态），新前端裁剪后 subpath 恰为 `v1beta/models/x:generateContent`（当调用方显式传带版本段的 path 时，见上节 ③ 推演）→ 防御剥掉 `v1beta/` → 上游收 `/v1beta/x:generateContent`，**把一个好请求改坏**。
   - 渠道 baseUrl `https://host/api`，上游真实存在 `/api/api/...` 形态网关（叠层路由并不罕见）→ 防御必误剥。
   - 任何「最后一段是通用词」的 baseUrl（`/openai`、`/proxy`、`/api`）都提高误剥概率，且服务端无法区分「旧前端的双拼」与「合法的同名前缀」——两者比特级相同。
3. **合同纯度**：方案 §二 已论证服务端是唯一权威、单一合同「subpath 相对 baseUrl」。防御在权威层为兼容过期客户端开第二个合同，此后每一条 proxy 探针断言都要携带这个历史包袱（方案 §三.3 第二条后端探针已显露出这一点：断言值悬置于裁决）。

**不加时的滚动窗口处置（建议写入任务书收尾）**：
- 部署即换 bundle 文件名（任务书步 5 已含 ff-merge），新名强制缓存失效，窗口 = 已打开页面的存活期。
- 窗口内旧 bundle 打 `/v1/v1/...` 收 404 == 部署前行为，用户刷新即愈；无恶化面，无需回滚预案。
- 可选观察项（非必须）：服务端日志按 `/v1/v1/` 特征 grep 一天，确认窗口收敛，不写代码。
- 后端探针第二条（旧前端形态）按「不加防御」写死断言：`/api/proxy/<cid>/v1/models`（base 带 /v1）→ echo path 为 `/v1/v1/models`（现状锁定，防未来有人无意改拼接）。
