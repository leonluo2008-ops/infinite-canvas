## 5. 服务端 B0 设计审计

- **事务骨架**：沿用 `_connect()`（WAL + busy_timeout 5000 + isolation_level=None，channel_seed.py:18-26 实读）+ `BEGIN IMMEDIATE`（:46 实读已在用）。「写标记 + 种入」同事务提交、异常整体 ROLLBACK → 原子，不存在「标记写了种子没种」或反向中间态。✅
- **并发**：BEGIN IMMEDIATE 串行化写者；ThreadingHTTPServer（test_multiuser_s1.py:29 实读）多线程下第二请求等锁后见标记即返回。探针③覆盖。✅
- **回滚**：异常 → ROLLBACK → 不写标记 → 下次 GET 重试。与现实现 :67-71 的静默回滚模式一致。✅
- **🔴 E1（BLOCKING）：存量账号未设计，B0 按方案字面实现修不掉它声称要修的缺陷，甚至制造新缺陷。**
  - 现库 5 个账号（owner/owner00/owner2/verifyuser/user133）全部**没有标记行**（channel_seed_state 是新表）。
  - 按方案 §3 B0 字面逻辑「不存在则写标记 + 种入三渠道」：owner（已有 3 条）首次 GET → 无标记 → **再种 3 条 → owner 变 6 条**，直接制造 A4 事故。
  - 若实现者自行改为「count>0 则跳过且不写标记」（即探针④「非空账户 GET 不改数据、**不写标记**」的字面义）：verifyuser 现有 3 条 seed 行、无标记；用户删光 → count==0、无标记 → **重新种回 3 条**——恰恰是方案 §2 自称要修的「删光即回灌」缺陷，对全部存量账号原样保留。
  - 正确设计：事务内 `count>0 ∧ 无标记` → **只写标记不播种**（视为「已服务过」）；`count==0 ∧ 无标记` → 写标记 + 播种。探针④须改为「非空账户 GET：数据不变、**写入标记**（此后删光不再回灌）」。
  - 该缺陷影响 A3/A7 对全部现存账号的判定，属开工前必改。
