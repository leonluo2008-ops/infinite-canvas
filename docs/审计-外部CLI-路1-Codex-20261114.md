## 1. 逐条发现

### F1 — BLOCKING：程序化弹窗路径枚举不完整，`use-plugin-host` 仍是漏网入口
- **证据**：
  - 方案卡 A 将“程序化来源”限定为：`use-agent-bridge.ts` 的 `run_generation` 分发。
  - 源码核对确认方案点名的链路成立：`use-agent-bridge.ts:63-71` 确实调用 `generateNodeRef.current(...)`；`project.tsx:3326-3338` 的 `handleGenerateNode` 在 `project.tsx:3335-3337` 因 `!isAiConfigReady(...)` 调 `openConfigDialog(true)`。
  - 但 `use-plugin-host.tsx:45-49` 也有独立的 `ensureReady()`：`!isAiConfigReady(config, config.model)` 时直接 `openConfigDialog(true)` 并抛错；`generateImage` / `generateVideo` / `generateText` 都会调用它（`use-plugin-host.tsx:53-83`）。这是另一个非 `handleGenerateNode` 的 AI 生成入口。
  - 方案 §四只声明保留 `pages/image/index.tsx`、`pages/video/index.tsx` 的手动路径，没有对 plugin host 做来源归类。
- **风险**：如果工作流或插件节点通过 `pluginAi.generateImage/Video/Text` 自动触发生成，卡 A 修完后该路径仍会弹全局配置 Modal；B3 只测 `run_generation`，会给出假阳性“已根治”。
- **修法**：
  1. 扩大卡 A 的来源分类清单，把 plugin host 的 `ensureReady()` 一并纳入。
  2. 明确规则：插件宿主若由自动执行/workflow 触发，按 `programmatic` 处理，不弹 Modal，把错误返回给插件/写入节点错误；若由用户点击插件 UI 触发，保留 Modal。
  3. B3 增加一条负向探针：渠道为空时触发 plugin AI 自动生成，断言全局 Modal 不弹出且错误可观测。

### F2 — IMPL-FIXABLE：`pollVideoNodeTask` 的“agent 驱动入口”没有对应到现有调用形态
- **证据**：
  - 方案说 `pollVideoNodeTask`（`project.tsx:426-432`）的非 silent 分支也要“agent 驱动入口同型处理”。
  - 源码显示 `pollVideoNodeTask(node, silent = false)` 只有 silent 布尔，没有 source 概念：`project.tsx:418-432`。
  - 当前自动恢复轮询是 `pollVideoNodeTask(node, true)`，silent 分支本来就不弹窗，只写节点错误：`project.tsx:577`、`project.tsx:427-430`。
  - 非 silent 调用位于 `handleRetryNode` 内：`project.tsx:3799`，更接近用户手动重试路径。
- **修法**：方案应把该点改成明确语义：自动恢复轮询继续走 silent / 节点错误；手动重试继续弹窗；只有确实存在“agent 创建的 video task 后续轮询”路径时，才在该路径显式传 source，不要把非 silent 的手动 retry 误改成 programmatic。

### F3 — IMPL-FIXABLE：`project.tsx:4095` 被方案称作“程序化调用方”，但当前形态是用户重试入口
- **证据**：
  - 方案风险 1 写：`handleGenerateNode` 还有其他程序化调用方，`project.tsx:4095 文本模式自动生成等`。
  - 源码显示 `project.tsx:4092-4095` 是 `handleNodeRetry`，节点重试时调用 `generateNodeRef.current(...)`。
- **风险**：实施者若按方案把该点标成 `programmatic`，用户手动点击重试时将不再弹配置框，违反方案“手动路径不变”的承诺。
- **修法**：修正分类：`handleNodeRetry` 默认 `source: "user"`。只有后续确认某些 retry 是 agent 自动发起时，才由实际发起方显式传 `programmatic`。

### F4 — IMPL-FIXABLE：卡 B 的“点击引导直达配置弹窗”缺少错误 UI 契约

### F5 — IMPL-FIXABLE：B3 的 Modal 探针判据还不够机器精确
- **证据**：方案写“`document.querySelector` 全局配置 Modal 不存在”，又说“可见 modal 计数 = 0”，但未给出选择器、可见性判定细节和重复触发间的状态清理方式。
- **风险**：AntD Modal 关闭后可能仍短暂存在于 DOM；不同实施者可能用 `querySelector` / `querySelectorAll` / `display:none` 判定得出不同结果。
- **修法**：
  1. 给全局配置 Modal 增加稳定 `data-testid`，或明确使用 `[role="dialog"]` + 已知标题。
  2. 判定统一为 `querySelectorAll(...)` 后过滤 `getBoundingClientRect().width > 0 && height > 0`。
  3. 每轮触发前记录/清零状态，触发后等待固定事件或 UI 稳定期，再断言。
  4. 渠道清空测试要写清是否使用独立 profile、如何 reset Zustand persist，避免污染所有者真实配置。

## 3. 独立前提问句的回答

**按这份方案做完，所有者“工作流执行时弹窗不再反复阻断我”是否达成？**

在方案假设的真实形态成立时——即所有者当前 `channels: []`、失败来自 agent 后端下发 `run_generation`、前端 `isAiConfigReady` 为 false——卡 A 能阻断该具体链路的反复弹窗。代码事实支持这个前提：`isAiConfigReady` 要求模型匹配到渠道且 baseUrl/key 满足条件（`use-config-store.ts:217-220`），而“本地代理”配置不在该判定内；因此“配好了本地代理但渠道凭据仍缺失”可以解释反复弹窗。卡 B 也能部分回应“不知道缺什么”，因为它把错误指向具体模型、缺失项和【配置→渠道】入口。

但按当前方案文本，还不能承诺“工作流执行期间弹窗次数 = 0”这一更强结论，因为 `use-plugin-host` 还有独立的 `openConfigDialog(true)` 程序化入口未纳入分类和验收。补齐 F1 后，才可对方案声明的场景做出可靠达成判断。

**如果所有者抱怨的真实形态不是本方案假设的那种，哪些部分是白做的？**

如果实际弹窗不是由 `use-agent-bridge.ts` 的 `run_generation → handleGenerateNode` 触发，而是由 plugin host、其他 agent 工具链路、或网关侧驱动的前端执行路径触发，那么卡 A 的核心改造——给 `handleGenerateNode` 增加 `source` 并只改 agent bridge 分发——对实际痛点基本无效；B3 针对 `run_generation` 的正向/重复触发探针也会变成与真实场景无关的验证。卡 B 若只挂在 `handleGenerateNode` / `pollVideoNodeTask` 的错误落点上，也可能不会出现在真实失败节点上。卡 C 的网关证据归档仍有价值；`openConfigDialog(true, "channels")` 的直达渠道能力可复用，但需要重新接到真实触发源的错误出口上。
