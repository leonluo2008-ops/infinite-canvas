# 探索：画布多用户 SaaS 化（技术路线调研）

- 日期：2026-11-15 开题
- 分支：`explore/saas-multiuser`（从 dev 拉出，探索专用；**技术路线未定前不动业务代码**）
- 背景：单人自用画布已服务器化跑通（Surface :3001 → bridge :8779，systemd 常驻，单人零密钥形态）。所有者想探索做成对外多用户 SaaS：用户打开网页即可用，对标聚创 `aigc.jxinai.com/#/canvas` 一类工具。
- 所有者点名的三个关键点：①代理 ②Agent ③模型渠道配置的服务器持久化

## 一、现状能力盘点（每个组件是什么/绑了什么单人假设）

### 1. web 前端（React + vite）
- 渠道/模型/偏好配置存在**浏览器 localStorage**（zustand persist，key `infinite-canvas:ai_config_store`），每个浏览器各自一份。
- `bootstrap-config`：首次空白打开时从同源 `/api/bootstrap-config` 拉预置渠道种入（幂等，已有 store 则跳过）。
- WebDAV 同步：用户可把配置同步到**自己的** WebDAV（凭据也在 localStorage）。
- vite dev/preview 的 `/api` 代理固定转发到 `127.0.0.1:8779`——**同机同域假设**。

### 2. bridge（wanrepro/ui/server.py，Python 纯标准库，:8779）
- 拆解/命名/传图/视频生成任务桥。**无用户概念**：单一 `uploads/ analysis/ projects/` 目录全员共享。
- 访问控制：`WAN_TOKEN` 单口令 gate（未设=直通），**单租户口令，不是账号体系**。
- 并发限制：拆解全局单槽（`ANALYZE_BUSY` 信号量），SDGF 生成全局 2 槽（`SDGF_JOBS`）。
- 拆解大脑密钥 `JXIN_API_KEY` 走服务端环境变量（已 systemd 注入）。
- CORS 白名单硬编码 `http://127.0.0.1:3000`/`localhost:3000`。

### 3. canvas-proxy（@basketikun/canvas-proxy，:23210）
- 132 行极简本地转发代理：浏览器 → `http://127.0.0.1:23210/https://目标` → 目标，只为绕浏览器 CORS。
- 无鉴权、不改写、key 仍在浏览器持有随请求转发、日志只在终端。
- **单人假设**：监听 127.0.0.1，README 明确警告不可 0.0.0.0 暴露（否则成开放转发器）。

### 4. canvas-agent（@basketikun/canvas-agent，:17371）
- 本地 Agent 桥：画布网页 ↔ 本机 Codex/Claude CLI。默认只监听 127.0.0.1。
- 首次连接 Origin 绑定（`~/.infinite-canvas/canvas-agent.json` 的 origins），token 单份。
- **单人假设**：一台电脑一个用户的 CLI 凭据；多用户下所有用户会共享同一个本机 Agent/凭据，且 Origin 绑定机制会被多 origin 打穿。

### 5. wanrepro 拆解引擎（pipeline/，本机已验证）
- 依赖：主链纯标准库 + ffmpeg；转写旁路 requirements.txt 四件套。
- 单机单实例，任务目录按任务 id 组织，无按用户分目录。

## 二、多租户差距清单（差距/影响/涉及文件/量级）

| # | 差距 | 影响 | 涉及 | 量级 |
|---|---|---|---|---|
| G1 | 无账号体系（WAN_TOKEN 是单口令开关） | 谁都能用、无用户边界、无配额 | server.py gate + 前端登录态 | **L** |
| G2 | 数据目录全员共享（uploads/analysis/projects） | 用户互相看得到/删得到对方任务 | server.py 目录组织 + task 命名 | M |
| G3 | 渠道/密钥配置在各自浏览器 localStorage | 换设备丢失；平台无法统一渠道/计费；密钥安全无管控 | use-config-store + 新增服务端配置存储 | **L** |
| G4 | 拆解全局单槽/生成 2 槽 | 多用户互相排队卡死 | server.py 信号量→按用户/按渠道分池 | M |
| G5 | canvas-proxy 本机伴生进程模式 | SaaS 用户不可能每人本机装代理 → **服务器形态下同源直连即可消除 CORS 需求**（proxy 的存在意义消失，需要的是服务端出网转发层） | 前端请求路由 + 服务端转发端点 | M |
| G6 | canvas-agent 绑定本机 Codex CLI | SaaS 用户无本机 CLI → 需服务器侧 Agent（每用户会话隔离/沙箱/凭据池） | canvas-agent 服务化改造 | **L** |
| G7 | 无配额/计费/用量审计 | 平台统一渠道时无法控成本 | 新增用量记账层 | M-L |
| G8 | 密钥安全：平台统一渠道=密钥在服务器；BYOK=用户密钥过服务器 | 信任模型必须先定 | 取决于路线选择 | - |
| G9 | CORS 白名单硬编码 | 反代/域名形态下预检失败 | server.py CANVAS_ORIGINS | S |

## 三、三个点名组件专项评估

### ①代理
单人形态的存在理由是「浏览器 CORS」。SaaS 形态下前端与后端同域（同一台服务器），**CORS 问题自然消失**；真正需要的是**服务端出网转发层**（平台代用户调渠道），它同时解决 G5 和密钥不出服务端的问题。canvas-proxy 本体在服务端形态下退役，其转发语义（原样转发/SSE 透传）可作为服务端转发端点的参考实现。

### ②Agent
现状强绑「用户本机的 Codex/Claude CLI」。SaaS 形态必须服务器侧 Agent 化，三种子形态（按投入排序）：
- a. 服务端跑 CLI 池（每用户会话绑定一个 CLI 实例，凭据平台出）——最快但凭据共享、审计复杂；
- b. 服务端 Agent 框架（直接调模型 API 实现画布操作 agent，脱离 CLI）——可控性最好，改造最大；
- c. 本期不做多用户 Agent（SaaS 首期砍掉 Agent 功能，画布生成能力先行）——最小可行。
依赖外部调研结论定夺。

### ③模型渠道配置的服务器持久化
现状 localStorage + WebDAV（用户自己网盘）。SaaS 形态的分裂点在**渠道归属**：
- 平台统一渠道：配置+key 全在服务端（复用 bootstrap-config 机制升级为服务端配置存储），用户零配置——配套必须做配额/计费（G7）；
- BYOK：每用户 key 存服务端 per-user 配置（加密落盘），平台只做工具；
- 混合：平台送基础额度 + 用户可加自己的 key 提额。
已有基础：`channel-config.json` 预置机制、config-store 结构清晰、WebDAV 同步代码可改造成服务端同步。
