# 方案 · S3.7 渠道 baseUrl 自带 `/v1` 时代理路径双拼

> 前置：大看板 `docs/开发计划书.md` 节点 S3.7；L2 `docs/项目适配包.md`。
> 实施仓 `E:\User\GitHub\infinite-canvas`（分支 `dev`，基线 HEAD `bc5705d`）；部署位 `:8780`。

## 一、现象与一手证据

Ollama Cloud 预置渠道 `baseUrl = https://ollama.com/v1`，用户填 key 后「拉取模型」/生成请求返回 404，上游收到的路径是 `/v1/v1/models`（双 `/v1`）。

代码取证（基线 `bc5705d`，行号以 `git show bc5705d:<path>` 为准）：

| 环节 | 位置 | 事实 |
|---|---|---|
| 前端绝对地址归一 | `web/src/stores/use-config-store.ts:543-548` | `buildApiAbsoluteUrl`：baseUrl 末尾不是 `/v1` 就补 `/v1`，然后拼 `path`。baseUrl 为 `https://ollama.com/v1` + path `/models` → `https://ollama.com/v1/models` |
| 前端转代转发地址 | `web/src/services/api/channel-proxy.ts:46-52` | `channelProxyUrl` 取 **绝对地址的完整 pathname**（`/v1/models`）作为 subpath：`/api/proxy/<cid>/v1/models` |
| 服务端拼接 | `wanrepro/ui/channel_store.py:695` | `target = base.path.rstrip("/") + "/" + subpath.lstrip("/")` → `/v1` + `/` + `v1/models` = **`/v1/v1/models`** |
| 探针现状 | `wanrepro/tests/test_multiuser_s1.py:120-131` | 渠道 baseUrl 全为**无路径**的 `https://93.184.216.34`，subpath 直接是 `/v1/chat`、`/v1beta/models` → 恰好正确，双拼从未被覆盖 |

结论：服务端合同是「subpath 相对 baseUrl」，前端却传「相对 origin 的绝对 path」。两者仅在 baseUrl **无路径**时重合，所以聚鑫 / SDGF 一直正常，只有 `ollama.com/v1` 暴露。

## 二、判定「哪个合同是对的」

- 服务端是**唯一权威**（S3.9 已定版：渠道只存服务端），且 `_forward` 的拼接是 B2 起就有的一行，改动它会同时影响 gemini `/v1beta`、SSE、所有既有探针。
- 前端 `channel-proxy.ts:9-11` 的注释本身就写着「服务端代转发是 `baseUrl.path + "/" + subpath`，自己不加 `/v1`」——**注释与实现矛盾**，实现（用完整 pathname）才是 bug。
- 因此正解 = 让前端按服务端合同传「相对 baseUrl 的路径」：剥掉 baseUrl 自带路径前缀。

## 三、改点（最小面）

1. `web/src/services/api/channel-proxy.ts`
   - `channelProxyUrl(config, absoluteUrl)`：新增「按 baseUrl 路径前缀裁剪 pathname」的一步。
   - `ChannelTarget` 增可选 `baseUrl?: string`；`channelApiUrl` / `channelAbsoluteUrl` 传入 `config.baseUrl`（两处调用方均已是 `AiConfig`，字段现成）。
   - 裁剪规则：`basePath = new URL(baseUrl).pathname` 去尾斜杠；若 `basePath` 为空 → 原样；若 pathname（大小写不敏感）等于 basePath → 用 `/`；若以 `basePath + "/"` 开头 → 切掉该前缀；否则原样（例如 gemini 的 `/v1beta/...` 与 baseUrl 路径不匹配时不动，交由上游返回真实错误）。
   - query 原样保留。
2. `wanrepro/ui/channel_store.py`
   - **不改拼接逻辑**（v1.1 已裁决，见 §8.1）：服务端合同保持「subpath 相对 baseUrl」，去重防御不采纳。
3. 探针（先写断言再改实现？否——本节点无「先删后改」依赖，断言与实现同批落地）
   - 后端 `wanrepro/tests/test_multiuser_s1.py` 代转发段新增两条：
     - 渠道 `baseUrl = https://93.184.216.34/v1`，请求 `/api/proxy/<cid>/models` → echo 上游收到的 `path` 必须是 **`/v1/models`**（`path.count('/v1') == 1`）。
     - 同渠道请求 `/api/proxy/<cid>/v1/models`（旧前端形态）→ 断言记录当前行为（若采纳防御则为 `/v1/models`，否则 `/v1/v1/models`），断言值以审计裁决为准，不写成模糊断言。
   - 前端 `web/scripts/probe-s3-7-proxy-url.mjs`（新建）：esbuild 打包 `channel-proxy.ts`，断言三形态：
     ① baseUrl 无路径 + `/models` → `/api/proxy/<cid>/v1/models`；
     ② baseUrl `…/v1` + `/models` → `/api/proxy/<cid>/models`（回归本缺陷）；
     ③ baseUrl `…/openai/v1` + path `/models`（绝对地址因此是 `…/openai/v1/models`）→ `/api/proxy/<cid>/models`（多段路径前缀裁剪）；
     ⑤ 成品链路 `channelMediaUrl`（同源、非自含凭据）在 baseUrl 带路径时同样走裁剪后的路径；
     ⑥ baseUrl 为空/非法（如 `""`、`"ollama.com/v1"`）→ 不裁剪、不抛错（原样返回）；
     ④ 无 channelId → 抛错（既有行为不回归）。

## 四、边界（禁发散）

- 不动：`buildApiAbsoluteUrl` 的 `/v1` 归一（本地直连仍需要它）；服务端 SSRF/白名单/密钥注入；单机版路径；渠道存储与 S3.9 语义。
- 不改 gemini `:action` 类地址的生成方式，只改「绝对地址 → 代转发地址」这一步的裁剪。
- 不新增依赖、不加配置项。

## 七、风险

1. **滚动部署窗口**：新 bundle 未加载的浏览器仍会发 `/v1/v1/...`。是否用服务端去重兜住 → 审计裁决点（见 §三.2）。
2. 裁剪规则对「baseUrl 路径与真实上游路径不同」的异常配置会原样透传（不猜），错误由上游返回。
3. `channelProxyUrl` 被 6 处调用（audio/image/video/lapian），裁剪只在 baseUrl 带路径时生效，无路径配置零影响。
