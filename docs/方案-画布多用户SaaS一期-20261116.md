## 一、目标与范围

**目标**：画布从单人自用升级为对外多用户 SaaS（对标聚创 aigc.jxinai.com 形态）：用户注册登录 → 打开网页即用；一期路线 C（BYOK 平台：每用户自带渠道 key，服务端加密自管+代转发），预留升级 B（平台统一渠道+积分计费）的存储与网关接口。

**一期范围（四件套）**：
| # | 交付物 | 对应差距 |
|---|---|---|
| D1 | 账号体系（注册/登录/session） | G1 |
| D2 | 渠道配置服务端持久化（每用户加密存储 + 代转发） | G3、G5、G8 |
| D3 | 数据按用户隔离（目录/任务/并发分池） | G2、G4 |
| D4 | CORS/部署适配（白名单、反代形态） | G9 |

**明确不做（一期）**：
- ❌ Agent 多租户（所有者拍板砍掉；canvas-agent 保持本地单人形态，与「Surface 服务器 Agent」另行立项）
- ❌ 积分/计费/支付（B 阶段再做；一期只埋用量审计埋点）
- ❌ 平台统一渠道（一期 BYOK；NewAPI 网关接入留 B 阶段）
- ❌ 协作/多人共享画布（远期）

## 二、核心设计原则（回应所有者关切：不影响现有画布功能）

1. **单人模式零改动**：不启用账号体系时（`MULTI_USER=0` 默认值）——gate 照旧直通、配置照走 localStorage、目录结构照旧、bridge 现有行为一行不改。多用户是加在原链路上的分流点（二开铁律 2），不是平行再造。
2. **复用优先清单**（动代码前先对，铁律 1）：
   - 渠道持久化 → 升级现成 `bootstrap-config` 链路 + config-store 结构（前端 store 不动）
   - 服务端代理 → 复用 canvas-proxy 转发语义（132 行参考实现）做 bridge 端点
   - 账号 → Open WebUI 式本地注册的标准做法；session 管理参考 WAN_TOKEN gate 改造
   - 加密存储 → LibreChat `user_provided` 模式（key 加密落盘，服务端解密代调）
3. **参数合同指回引擎**：前端任何新增（登录态、渠道存取）都走 config-store 既有 action，不在前端另抄一套存取逻辑（铁律 7）。
4. **回归验收硬性化**：单人链路探针（入口 200 / 传图 / 拆解 / 生成结构核对）原样进回归清单，升级后必须全绿；单人链路坏=FAIL 不打折（零兜底）。
5. **部署可回滚**：Surface systemd 双 unit，新版上线前旧产物保留，`systemctl` 一条回退。

## 三、技术设计（一期 BYOK）

### 3.1 账号体系（D1）
- bridge（Python 纯标准库）新增：用户表（SQLite，标准库 `sqlite3`）、注册/登录端点、session token（httpOnly cookie）。
- 密码：`hashlib.scrypt`（标准库，无新依赖，符合 bridge 零 pip 依赖现状）。
- 开关：`MULTI_USER=0`（默认）时全部新端点关闭、gate 走现 WAN_TOKEN 逻辑——单人部署零感知。
- 注册策略：开放注册 or 邀请码（`INVITE_CODE` 环境变量，复用「邀请返积分」借鉴点的雏形）——**待拍板 Q3**。

### 3.2 渠道配置服务端持久化（D2）
- 存储：SQLite `user_channels` 表（user_id, name, baseUrl, apiKey_encrypted, apiFormat, models_json）；key 用 scrypt 派生密钥 AES 加密（或 Fernet 需引入 cryptography——**依赖取舍待审计**，优先纯标准库方案）。
- 前端：config-store 增加「服务端模式」数据源分流：`MULTI_USER` 站点登录后读写 `/api/user/config`，未登录/单人站点照旧 localStorage——**同一 store action，两个后端**。
- 服务端代转发：bridge 新增 `/api/proxy/<目标URL>`（canvas-proxy 语义：原样转发、SSE 透传、不落盘、只记访问日志行）；前端渠道请求在服务端模式下改走该端点，key 不下发浏览器。
- 旧 bootstrap-config 预置机制保留：站点管理员可设全站默认渠道（新用户开箱即用）。

### 3.3 数据按用户隔离（D3）
- 目录：`uploads/<user_id>/`、`analysis/<user_id>/`、`projects/<user_id>/`；`MULTI_USER=0` 时 user_id 恒为 `local`，路径与现状**逐字节相同**（保证单人零改动）。
- 并发：拆解槽/生成槽按用户限额（如每用户 1 拆解 + 1 生成），全局上限保留（Surface 4核16G 撑得住的量，**具体数值待审计**）。
- 访问控制：任务/文件端点校验属主。

### 3.4 CORS 与部署（D4）
- `CANVAS_ORIGINS` 改为环境变量可配（默认值保持现状）；反代形态下透传 Origin 校验。
- 部署：仍 systemd 双 unit（web :3001 + bridge :8779）；新增环境变量进同一个 `EnvironmentFile`。

## 四、批次计划

| 批次 | 内容 | 验收判据 |
|---|---|---|
| S1 | D1 账号体系 + MULTI_USER 开关骨架 | 注册→登录→session 生效；开关关闭时全站行为与现状逐字节一致（单人回归全绿） |
| S2 | D2 渠道持久化 + 代转发 | 登录用户配渠道→换设备登录配置还在；key 服务端加密落盘（盘上零明文）；代转发实测（含 SSE 流式）；未登录站 bootstrap 预置照旧 |
| S3 | D3 数据隔离 + 并发分池 | 两用户互不可见对方任务；并发限额生效；`local` 路径与现状一致 |
| S4 | D4 CORS/部署 + 全链路验收 | Surface 真机：注册→登录→配渠道→传图→拆解→生成 全链路 PASS + **单人回归全绿** + 回滚演练一次 |

每批次：双路审计（分通道：现有通道 + GPT 6 Luna 档）→ 执行 → 真机验证。Git 管理全程：功能分支 + 显式路径提交 + 推 fork。

## 六、红线继承

- 只加部署壳/分流点不改单人行为语义；业务代码改动全部走功能分支。
- 文档/日志/命令行历史零明文密钥；用户 key 加密落盘，运维命令不回显。
- 验证零兜底：FAIL 如实记；单人回归链路必须全绿。
- 本机开发环境（8776/8779/vite:3000）不动不停；Surface :8888 Hindsight 不影响。
