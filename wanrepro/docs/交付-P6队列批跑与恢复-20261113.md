## 一、这一卡把什么变成了「批次能力」

P4 会跑一个实例（拉片→组装→自检→停在待批），P5 会记录一批实例的身份与派生状态。P6 补的是中间那层：
**一批实例怎么排队跑、跑出渠道拥塞怎么办、回执丢了怎么办、跑一半刷新了怎么办**。

```
                     ┌──────────────────────────────────────────────┐
批次 N 实例 ─────────▶│ runBatchQueue（并发上限 3，实例级）           │
（BatchRecord.members）│  ① 取槽 → ② job.prepare（P3，幂等）          │
                     │  ③ job.run（P4 runWorkflowInstance，不复制）  │──▶ 待批 / canvas_ready
                     │  ④ 失败分类：拥塞→退避重排 / 未知提交→对账 / 其它→失败│──▶ failed（不误判他例）
                     └───────────────┬──────────────────────────────┘
                                     │ 簿记（attempts/退避时刻/提交守卫/上次结局）
                                     ▼
                        BatchRecord.queue（随 CanvasProject 持久化 + 导出同路）
                                     │ 刷新
                                     ▼
                        planBatchResume（派生状态优先）→ 只跑没跑完的
```

三条硬口径（卡上红线 25 + D11）：

1. **不复制编排**：单实例一律调 P4 `runWorkflowInstance`，状态一律由 P5 `deriveInstanceStatus` 现查。
2. **不新写轮询器**：对账只调 P5 `workflow-batch-query` 的既有查询口径（`buildGenerationStatus`）。
3. **队列条目只记排队簿记**（尝试次数、退避时刻、提交守卫、上次尝试结局），**不存「实例现在怎么样」**；
   两者冲突时以派生器为准（`planBatchResume` 就是这么写的）。

## 二、渠道拥塞分类：429/409 与「未知提交」是两条路

审计 §5.2 的原话是：同节点重触发会 abort 前一次，但**渠道侧任务仍在跑**、正处在扣费窗口。所以这两种错误
绝不能同等对待——一个是「没进去」，一个是「不知道进没进去」。

| 分类 | 判定依据（`workflow-channel-failure.ts`） | 语义 | 队列处置 |
|---|---|---|---|
| `rate_limited` | HTTP 429、`限流/频率/429/too many requests/请求过于频繁` | 已明确拒绝，**未提交** | 指数退避重排队，不算失败 |
| `slot_busy` | HTTP 409、`单槽/正在跑/同时只认/409` | 已明确拒绝，**未提交**（槽被占） | 指数退避重排队，不算失败 |
| `submit_unknown` | HTTP 5xx、超时/timeout/回执/连接中断；以及**任何无法确定是否已提交**的异常 | **可能已提交**，渠道侧可能在跑并扣费 | **只对账，禁自动重发**；查不到 → explicit-unknown 停住交人 |

判定优先级（**这条顺序是本卡最容易写错的地方**）：先判 `submit_unknown` 再判拥塞——因为「请求发出去了但
回执丢了」的报错文本里经常同时带着「请稍后再试」，若先判拥塞就会被当成 429 重发一次，**多扣一次钱**。
分类器里 `5xx` / 超时 / 未知一律落到 `submit_unknown`，宁可按未知处理交人，也不猜。

`409` 的语义在服务端亲读过，不是猜的：

```
wanrepro/ui/server.py:151   ANALYZE_BUSY = threading.Lock()          # 拉片槽
wanrepro/ui/server.py:735   WAN_BUSY = threading.Lock()              # 万相单槽（CLI 同时只认一条，并发会重复扣费）
wanrepro/ui/server.py:1135  SDGF_JOBS = threading.BoundedSemaphore(2) # 生成槽，并发上限 2，第三条 409
wanrepro/ui/server.py:3670  ANALYZE_BUSY.acquire(blocking=False)      # 拉片入口抢的是另一把锁
```

三把锁是**三个独立对象** → 拉片与生成互不占用（P0a 推测#1 至此关闭：成立）。也就是说 409 在本项目里
意味着「别的实例占着槽」，是**排队信号**，不是失败信号。

## 三、退避参数（数值与理由，常量写死在代码里）

| 常量 | 值 | 为什么是这个值 |
|---|---|---|
| `BATCH_CONCURRENCY_DEFAULT` / `..._MAX` | 3 | 卡上 D1 规定「并发 3 起步」；服务端生成槽只有 2（`SDGF_JOBS`），实例级并发 3 意味着偶发 409 是常态，正好由退避吸收；再调高只会把 409 打成刷屏 |
| `BATCH_BACKOFF_BASE_MS` | 4000 | 万相单槽的典型占用是 10–40s 量级；4s 起步既不会空转也不会把槽堵死 |
| `BATCH_BACKOFF_FACTOR` | 2 | 指数退避：4s → 8s → 16s → 32s |
| `BATCH_BACKOFF_MAX_MS` | 60000 | 封顶 60s：超过一分钟的等待，人已经该看到「渠道持续拥塞」而不是盯着转圈 |
| `BATCH_CONGESTION_MAX_RETRIES` | 4 | 累计最多等 4+8+16+32=60s；再等下去说明不是瞬时拥塞，如实失败并给可读文案交人（不无限重试） |
| `BATCH_INSTANCE_MAX_ATTEMPTS` | 6 | 同一实例**跨刷新**累计编排尝试上限，防「续跑→失败→再续跑」死循环 |
| `BATCH_SUBMIT_RECONCILE_ROUNDS` / `..._INTERVAL_MS` | 2 / 15000 | 两轮 × 15s：吃掉「后端任务列表滞后」的窗口；两轮都查不到就是真查不到 |

拥塞重排**不吃失败预算**：`congestionRetries` 与 `attempts` 分开计（前者=429/409 命中次数，含最后那次终判）。

## 四、未知提交对账（B6 关闭判据）：先写后发 + 只查不重发

三步，顺序不可换：

1. **守卫先落盘**（`guardedBatchSubmit`）：把「我要提交什么」（节点、provider、请求指纹）写进
   `BatchRecord.queue.entries[].submitGuard` 并**真 flush 到项目**，然后才发请求。
   *守卫落盘失败 → 拒绝发请求*：宁可不跑，也不留「钱花了但盘上没记」的坑。
2. **回执分类**：拿到 taskId → 立刻补写 `receipt` 再落盘；明确被拒（429/409/4xx）→ 清守卫（确认没提交）；
   **回执丢失** → 守卫**留在盘上且没有 receipt**，这就是对账入口。
3. **对账**（`reconcileBatchSubmit`）：按 P5 的既有查询口径核对
   - ① 按成员节点集查既有任务（`buildGenerationStatus`，块 ≤100）
   - ② 按已知任务号单查（节点残留 taskId 等线索）
   - ③ Wan 成片映射交叉核对（S2 的 job→成片 taskId 若已存在，说明提交确实发生过）
   - 命中 → `resolved`：**按 taskId 续查，不重建**；两轮都无 → `explicit_unknown`：停住交人，
     `planBatchResume` 会把它一直留在 `heldSubmitUnknown` 里，**自动层永不重发**。

探针实测（`probe-summary.json → unknownSubmit`）：

```
resolved        : 对账第 1 轮命中 13 条既有后端任务：按 taskId 续查，不重建
explicit_unknown: 对账 2 轮均未找到该提交对应的后端任务：标 explicit-unknown 交人裁决，自动层不重发
两种情况生成调用次数均 = 1（零重发、零重复付费）；守卫已随项目落盘（磁盘 payload 含 requestDigest）
```

## 五、暂停/恢复：暂停停在安全边界

- `shouldPause()` 触发后：**不再起新实例**，但**在途实例跑完才返回**。这一点是实测抓出来的：先前的实现
  直接 `break`，返回后 2 个在途实例变成孤儿——它们的结果会在调用方「已收口」之后写回聚合，UI 显示
  「已暂停」而实际还在跑。现已 `await Promise.all(in-flight)`，单测 `D` 段有专门用例守这条。
- 刷新/重开：`planBatchResume` 按 P5 派生状态决定——已到终点（待批/已批/生成中/完成）的跳过；
  盘上有无回执守卫的先对账；尝试预算耗尽的停住；其余按 `instanceIndex` 顺序续跑；
  `prepareNeeded` 只在「成员节点不在画布上」时给出 → **已落库实例不重新 materialize（不重拉片、不重建节点）**。

探针实测（5 实例批、并发 3、第 2 个收口时暂停）：

```
phase=paused, 已完成 3（#11/#12/#13）, 未起跑 2（#14/#15）
新进程真 rehydrate：队列簿记（concurrency=3, entries=5, phase=paused）完整恢复
续跑计划：run=[#14,#15] / skippedDone=[#11,#12,#13] / prepareNeeded=[#14,#15]
续跑后 5 个实例全部到待批；已完成实例的 lapian /run 调用数与生成调用数均不变（各 1 → 1）
```

## 六、Wan 成片映射持久化（S2）

问题：`job → 成片 taskId` 原本只存在 `localStorage['wan_video_file_tasks']`，**只留 200 条、导出不带、
清浏览器就没了**——批量跑一多，成片和 job 的对应关系就断（断了就只能靠人肉猜，正是卡上 S2 要治的）。

改法：**项目是唯一真源，localStorage 降为兼容视图**。

| 层 | 文件 | 职责 |
|---|---|---|
| 纯逻辑 | `wan-file-task-map.ts` | 老 200 条载荷解析/回写（旧行为逐字保留）、与项目表合并成一张视图（>200 条不丢） |
| 绑定层 | `wan-file-task-project.ts` | 认当前 `projectId`，写 `CanvasProject.workflowWanFileTasks`；项目不在 store 时给可见 warning（本会话仍可用） |
| 项目结构 | `use-canvas-store.ts` | `CanvasProject.workflowWanFileTasks`（与 `workflowInstances`/`workflowBatches` 同族落点）+ 导入显式透传 |
| 生产接线 | `services/api/video.ts` | 写：项目表 + 老 localStorage 双写；读：项目表优先，回落老 localStorage |
| 页面绑定 | `pages/canvas/project.tsx` | 打开项目时 `bindWanFileTaskProject(projectId)` |
| 批次成员 | `workflow-batch.ts` | `WorkflowBatchMember.wanFileTasks`：成员身上也带一份，批次聚合可查 |

探针实测（走**生产** `createVideoGenerationTask`，axios adapter 替身 → 零真实网络）：

```
创建 1 条 → 项目登记表 {job: wan-job-s2, fileTaskId: wan-file-s2}
老 localStorage 键同时写入（兼容）→ 随项目 flush 落盘

```

## 九、没做的（明确边界）

- 自修/自动匹配（P7）：本卡只到「如实失败 + 交人」，不做任何自动修补。
- 侧栏 UI（P8）：队列只有数据层与执行器，没有任何界面。
- 队列暂停只做了「安全边界暂停」，没有做「实例跑到一半强行中止」（那是 abort 语义，属于审计 §5.2 的扣费窗口
  问题，需要先把渠道侧取消能力做实，不在本卡范围）。
