# 审计：HUB_JOBS 全生命周期写入点（消除同类残留）

> 卡片：t_408a0867（根卡 t_abc4e7bf 的审计子卡）
> 代码基线：`feat/automation` @ 2a99e7f（A/B 两卡修复已入） + 本次审计改动
> 结论口径：**只认代码行与探针实数**，不写"应该没问题"。

## 0. 先说结论（TL;DR）

1. 缺陷本质确认：`HUB_JOBS` 的内存 job 记录**没有单一权威出口**——终态散在 4 个写入点，
   "是否活跃"散在 3 套口径（一套带心跳豁免、两套纯看 `status=="running"`）。强制结束那条
   只是最先被所有者撞到的那个落点。
2. **除 force_finish 外，修复前确实还有 3 条路径会留下"进程内永不自消"的 running 残留**（§2 已按严重度排）；
   **修复后不再有**：任何创建点都有与之配对的终态出口，"进得去出不来"的路径为 0。
   唯一剩下的"记录消失"场景是**进程被强杀**——内存态随之蒸发，不构成残留（子进程由启动对账按磁盘证据接管）。
3. 已做**最小改动**（不动并发模型、不动状态机、不动付费链协议）：新增统一终态出口
   `_finalize_job`，把 5 个终态写入点全部收口；`_spawn` 三个出口补齐终态；`_spawn_process`
   Popen 之后的窗口加保护；`_active_submit`（付费提交闸）改用带豁免的统一谓词；
   `_spawn` 补 60s 周期心跳（让"心跳新鲜"对线程 job 恒等于"真的在跑"，否则放宽就是重复付费风险）。
4. 机器证据：新探针 `automation/probe_job_lifecycle.py` **41/41 PASS**；受影响回归全绿（见 §6）。

## 2. 风险清单：修复前仍可能留下永久 running 的路径（按严重度）

|---|---|---|---|---|---|

| P0-2 | 高 | `_spawn_process` 在 `HUB_JOBS[...] = running` 之后、Popen 之前的 `argv_builder` | 命令拼装抛错（配置/路径畸形） | 记录 running，无 pid、无 reaper、永不收尾（拆解链） | ✅ `argv_builder` 异常 → `_spawn_failed` 落 failed |

| P1-2 | 中高 | `_spawn_process` 的 reaper 起线程 | 线程起不来 | 记录 running + 活子进程，永远没有终态出口 | ✅ 当场 `_finalize_job(failed)` 并在 error 里点名子进程仍在跑 |
| P2-1 | 中 | 线程 job 无周期心跳（渲染只打首尾、万相提交 `pct=None` 不打） | 单段 >900s | 看门狗 `held_job` 读不到"活证据"→ 把**真在跑**的任务降级 failed（误杀）；UI"提交在途"判据失效 | ✅ `_spawn` 补 60s 周期续打（记录进终态即停打） |

### 回答提问：除 force_finish 外，还有没有路径会产生永不自消的 running 残留？

**修复前：有，3 条**——P0-1（`_spawn` 的线程起不来/BaseException）、P0-2（`_spawn_process` 的 argv 构造）、
P1-2（reaper 起不来）。P1-1 是同一窗口的伴生形态。

**修复后：没有。** 判定依据是三条不变量（新探针逐条机器判定，见 §6 的 [1][3][5][6]）：
1. 创建点恰好 2 处，都紧跟一个"无论如何都会执行"的终态出口；
2. 源码里不存在 `status=done/failed` 的直写（`_finalize_job` 是唯一出口）；
3. 活跃判定只走 `_job_blocks_retry`/`_job_alive`——即使将来再出现一条漏收尾的记录，它也会在
   ≤900s 后被判僵尸而不再阻断任何操作（**兜底豁免**），不会复现"永久拒绝"。

## 3. 本次最小改动（逐条）

1. **统一终态出口** `_finalize_job(job_id, status, *, note, local_id, kind, **fields)`（:593）
   - 入参只接受 `JOB_TERMINAL_STATUSES = ("done","failed","force_finished")`，传 running 直接 `ValueError`；
   - 就地 `update`，不换 dict 对象；首个终态权威（人工强制结束后晚到的线程不得翻回 done/failed，
     冲突记 `terminal_conflict`）；记录不在且没给 `local_id/kind` 时返回 None（不凭空造记录）。
2. **`_spawn` 三出口补齐**（:626）
   - `except BaseException` → `_finalize_job(failed)` 后按需重抛（SystemExit 不吞）；
   - 线程起不来 → `_finalize_job(failed)` + `heartbeat_finish(spawn_failed)` + `HubError`；
   - 新增 60s 周期心跳线程（`heartbeat_beat(expected_run_id=job_id)`，记录进终态即停打）。
3. **`_spawn_process` 窗口保护 + argv 失败落终态**（:763）
   - `argv_builder` 异常 → 走 `_spawn_failed`（写死证 + failed 记录）；
   - `pid_created_at`/`heartbeat_attach` 异常 → 记 `attach_error`，reaper 照起；
   - reaper 线程起不来 → 当场 `_finalize_job(failed)` 并点名子进程仍在跑。
4. **`_spawn_failed` / `_reap` / `_finish_running_jobs` 全部改走 `_finalize_job`**（:736 / :742 / :1507）。
5. **`_active_submit` 收口到统一谓词**（:486）：`_job_running_records` + `_job_alive`，与重试守卫、
   删除合同同一份口径；真在跑的线程 job 由周期心跳保证"心跳新鲜 = 真的还在跑"。
6. **合同写进代码**（模块顶部 `HUB_JOBS` 声明处，:61-70）：创建点、终态出口、判活谓词三条硬约束。
7. **夹具同步**（判据收口的必然结果，不是放宽断言）：`probe_revoke_guard.py` 与 `probe_at16_b5a1.py`
   里"活跃提交"夹具补 `started=现在`——不带 `started` 的 running 记录按新口径就是"僵尸"，
   那本来就该放行；这两个断言考的是"真活跃仍被拦"，语义不变。

## 4. 只写进报告、未实施的建议（涉及并发模型/大范围重构，按卡片边界不擅自做）

1. **记录淘汰**：`HUB_JOBS` 无上限；可加"终态记录保留 N 条/N 小时"的裁剪（需先确认 GET 落账面
   的追溯期要求）。
2. **reaper 起不来时是否终止子进程**：当前选择"记录落 failed + 让子进程继续跑，状态由磁盘证据接管"。
   若要强一致，需要 Job Object / 进程组句柄（属并发模型改动）。
3. **`_active_submit` 按 kind 过滤**：现在任何 kind 的 running 都算"提交占用"；收紧成
   `kind=="hub-submit"` 可减少误挡，但要同步评估 `submit_view` 读面语义。
4. **落账面持久化**：job 记录跨重启就没了（GET 404）。若要"重启后仍能查上一次 job"，需要落盘，
   属数据模型新增。
5. **`_job_running_records` 直接删除**：它只做枚举、由 `_job_alive` 过滤；可合并进 `_job_blocks_retry`，
   但会牵动 3 个调用点与探针，收益低。

## 6. 合同（代码内已写死，后来者照此改）

- 创建 job 记录只允许 `_spawn` / `_spawn_process`；
- 终态只允许 `_finalize_job`，取值 ∈ `done / failed / force_finished`；
- 「是否活跃」只允许 `_job_blocks_retry`（或其布尔投影 `_job_alive`），口径 = 60s 启动宽限 + 900s 心跳豁免；
- 线程模式的 job 必须带 `heartbeat_dir`（周期心跳），否则 900s 后会被判僵尸（这是豁免机制的前提，不是可选项）。
