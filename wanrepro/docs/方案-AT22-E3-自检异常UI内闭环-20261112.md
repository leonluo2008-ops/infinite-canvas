## 0. 结论摘要

| 项 | 结论 |
|---|---|
| 主路 | 自检异常区每条发现行内点「改这一行的描述」→ 就地编辑 → 点「保存并重渲染」→ 服务端一次请求内完成「写清单第 8 列 → 重出提示词 → 重算审批快照 → 自检重跑 → 音频门禁重跑」→ 面板就地刷新 |
| 状态机 | **不改状态机**：`awaiting_approval` 原地重渲染（照 AT-17 B3 的既有先例），不新增 `awaiting_approval→rendering` 非法边 |
| 复用 | 写清单复用 `automation.replace`（唯一写层）；重渲染复用 `generate.rerender_for_audio_mode` 抽出的一处原地重渲染；自检复用 `selfcheck.run_selfcheck`；编辑承载是**一个**组件两处用（本卡 + AT-21） |
| 用户代价 | 2 次点击 + 输入；0 次离开当前页面；0 次磁盘操作；接口往返目标 ≤ 3s（本机 bridge 渲染为秒级，`hub_api.do_render` 自述"秒级，同步"） |
| 兜底 | 「退回置换」保留；磁盘改 md 仅**运维兜底**，不进任何产品文案 |

## 1. 现状核实（代码级）

### 1.1 今天用户被指向磁盘的那一条链

`绑图行残留`（自检②）FAIL 时，处理文案由 `automation/selfcheck.py:73-77` 的 `_how_prompt_word(bridge_id)` 产出：

```python
# automation/selfcheck.py:73-77（现状原文，**删除对象**——仅用于对照定位，不是操作指引）
def _how_prompt_word(bridge_id: str) -> str:
    return ("点「退回置换」回到待置换区，在清单 analysis/reverse/{b}/{n} 这些行的"
            "「用我的描述」列改写（删掉原物词），再确认置换重渲染（提示词按清单重出）"
            ).format(b=bridge_id or "&lt;桥id&gt;", n=replace.LIST_NAME)
```

调用点唯一：`automation/selfcheck.py:384`（`_check_residue` 的 `说明.处理`）。全库（`automation/ ui/ pipeline/ web/src`）除此一处外，**没有任何**把用户导向磁盘 markdown 的文案；其余 `HOW_*`（`selfcheck.py:53-61`）指向的都是真实 UI 动作（退回置换 / 重传（覆盖）/ 移除 / 知道，按原样 / 成组 / 重试）。

### 1.2 「用我的描述」在读写两侧的真实位置

| 层 | 位置 | 现状 |
|---|---|---|
| 数据列 | 清单第 8 列（`cells[7]`） | 渲染器读：`pipeline/reverse/render.py:1550/1556`（`decode_user_desc(cells[7])`），`Entity.shape`（`render.py:1462-1466`）**优先取它**，非空则整段替换原物描述 |

| 画布链写 | `ui/server.py:370-372` `set_checklist_desc` → `_update_checklist_cell(index=7)`，编码 `encode_desc_cell`（`server.py:283-288`），HTTP=`POST /api/desc/<id>`（`server.py:2601-2612`） | **画布链**可写；任务根是 `analysis/reverse/<id>` |
| hub 链写 | 无。`ui/hub_api.py:2346 set_asset` 只有 `image_url/clear/text(命名列)/decision` | **hub 链不可写** → 这才是「去磁盘改」的根因 |
| hub 读 | `automation/cards.py:508-531` 卡片字段有 `描述`（=第 3 列"模型看到什么"），**没有**「我的描述」 | 前端无从预填 |

补充：残留词表取自 `render.entity_noun_core`（`render.py:1218-1229`，**命名优先、否则"模型看到什么"**）——不含 `my_desc`。这意味着"改描述"能把原物词从正文里挤出去（`Entity.label()` 换成 my_desc），但词表本身不因改描述而缩小；改完再报残留是**合法结果**，UI 必须允许二次迭代（见 §3.3 的「成功但该项仍 FAIL」一行）。

### 1.3 为什么必须"原地重渲染"而不是走 `rendering`

`automation/state.py:35-37` 的 `_ORDER` 只允许逐级前进（`transition` 守卫在 `state.py:166-171`）：`awaiting_approval → rendering` 是非法迁移。今天要重出提示词，唯一合法路径是 `rollback_to_assets`（`state.py:209-231`，会**删掉** `提示词.md` 与 `自检.json`）再确认置换。

但 AT-17 B3 已经开了先例：`generate.rerender_for_audio_mode`（`automation/generate.py:233-263`）在 `awaiting_approval` 内**原地**重渲染——不迁状态、换正文、重算 `approval_snapshot`、自检与门禁一起重跑；`hub_api.set_audio_mode`（`ui/hub_api.py:986-1015`）在同一把 `task_lock` 内串起来并把新结果直接回显。E3 就是这条形态的第二个用户。

> 结论：E3 复用「原地重渲染」，不新增状态边、不造第二套渲染链。

## 3. 交互设计

### 3.1 入口位置（行内为主，侧栏不做）

```
┌ 提示词 ────────────────────────────────────────────────────────────┐
│ 自检 ⚠ 2/5 项异常                                                    │
│ ┌────────────────────────────────────────────────────────────────┐ │
│ │ ⚠ 绑图行残留        异常                                        │ │
│ │   提示词正文还留着我方要换掉的原物描述词：3 处（涉及行 #3）      │ │
│ │   原因：#3 的「双耳奖杯」残留于正文: …取出双耳奖杯造型香水…      │ │
│ │   怎么处理：点下面这条发现上的「改这一行的描述」…（§4.6 文案）   │ │
│ │   · #3 图2 「双耳奖杯」残留于正文: …取出双耳奖杯造型香水…        │ │
│ │                        [改这一行的描述]  ← 行内按钮（本卡新增）  │ │
│ │   ┌ 就地展开（同一位置，不弹窗、不换页） ─────────────────────┐ │ │
│ │   │ 第 3 行（组 #3+#5 一起改）  现用描述：（空=沿用原物描述）  │ │ │
│ │   │ ┌───────────────────────────────────────────────────────┐ │ │ │
│ │   │ │ 客户款双层玻璃香水瓶，哑光磨砂瓶身，无花纹            │ │ │ │
│ │   │ └───────────────────────────────────────────────────────┘ │ │ │ │
│ │   │ 原物描述（只读）：双耳奖杯造型香水小物体。表面为…        │ │ │ │
│ │   │ 留空＝沿用原物描述（原物词会被带回正文）  12/200         │ │ │ │
│ │   │                          [取消]  [保存并重渲染]          │ │ │ │
│ │   └───────────────────────────────────────────────────────────┘ │ │ │
│ └────────────────────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────────────┘
```

| 位置 | 形态 | 何时出现 |
|---|---|---|
| **主入口** | `绑图行残留` 条目的每条**发现行**尾部按钮「改这一行的描述」→ 点开后在该行**下方就地展开**编辑块 | 发现带 `行号` 且带 `可修` 声明时（§4.1）。`awaiting_approval` / `approved` / `generating` / `done` / `failed` 都可见，但按钮按状态置灰（§4.5） |
| 副入口 | 待置换区资产卡底部「用我的描述」一行（常驻，可空） | 仅 `awaiting_assets`（`AssetSection` 只在该态渲染，`task-detail-drawer.tsx:375-383`）；此处保存**不重渲染**（确认置换时自然带上） |
| 兜底入口 | 详情底部「退回置换」（`task-detail-drawer.tsx:3224`，弹窗文案 `:2897-2910`） | 既有，不改；文案补「（兜底）」 |

不做侧栏 / 不做全屏弹窗：证据（词 + 正文片段）就在上方，弹窗会遮住它；行内展开是 1 次点击。

### 3.2 编辑控件

| 项 | 规定 |
|---|---|
| 控件 | 多行文本域（`variant="cell"` 用正文字体、默认 3 行自适应、上限 8 行）；**不**用等宽代码编辑器（提示词编辑 `variant="doc"` 才等宽） |
| 预填 | `asset_cards[n].我的描述`（§4.1 新增字段），空串则空 + placeholder=原文只读参照「原物描述」 |
| 留空语义 | 清空＝回到"按原物描述渲染"。必须显式提示「留空＝沿用原物描述（原物词会被带回正文）」——不静默 |
| 换行 | 保存时按既有 `set_asset(text)` 写法 `re.sub(r"\s+", " ")` 折叠为单空格（描述要进 `@图片N 名字（描述）` 括号内，换行会破坏表格与正文） |
| 长度 | 软提示 200 字（计数器变黄），硬上限 500（服务端 400） |
| 快捷键 | `Ctrl/Cmd+Enter`＝保存并重渲染；`Esc`＝取消（有改动先二次确认） |
| 不自动保存 | 每次保存都会重渲染+自检（有成本、会产生新一代提示词与快照），禁止逐键保存 |
| 组联动 | 该行在确认组内 → 标题显「组 #a+#b 一起改」，保存时整组写（§4.4）；组内行描述必须一致，否则同一张图两个描述 |
| 脏态 | 与基线不同才算可保存；未变更时「保存并重渲染」置灰 |

### 3.3 状态机（编辑器三态）

```
                    ┌──────────┐  点「改这一行的描述」
                    │  closed  │──────────────┐
                    └──────────┘              ▼
                                         ┌────────┐  改字   ┌───────┐
                                         │  idle  │────────►│ dirty │
                                         └────────┘◄────────└───────┘
                                              │  改回原位      │ 点「保存并重渲染」/ Ctrl+Enter
                                              │                ▼
                                              │          ┌──────────┐  写清单+取正文+落盘快照
                                              │          │  saving  │──────────────┐
                                              │          └──────────┘              ▼
                                              │                               ┌───────────┐
                                              │                               │ rendering │ 自检+门禁
                                              │                               └───────────┘
                                              │                                     ▼
                                              │                              ┌────────────┐
                                              │                              │  checking  │
                                              │                              └────────────┘
                                              │                         成功  ▼        ▼ 失败
                                              │                        ┌───────┐  ┌────────┐
                                              └────────────────────────│ done  │  │ failed │
                                                                       └───────┘  └────────┘
```

| 阶段 | 界面（三态提示） | 编辑器 | 按钮 |
|---|---|---|---|
| `saving` / `rendering` / `checking` | 「正在保存并重渲染…（写清单 → 重出提示词 → 重跑自检）」+ 细进度点 | 只读 | 全部 loading/置灰 |
| **成功且该项转 PASS** | 「已保存并重渲染：这一项自检已通过 ✓（自检 N 项全绿）」 | 收起，显示新值 | — |
| **成功但该项仍 FAIL** | 「已保存并重渲染：提示词里还有 2 处残留（见下方更新后的发现）」——**同位置替换**，不新增第二个红条 | 保持展开（连续迭代） | 可再次保存 |
| **失败** | 见 §3.5 失败矩阵；红色行内条 + 原文（不 toast-only） | 保持展开，草稿不丢 | 「再试一次」「取消」 |

成功判定不用前端推断：服务端回显新 `自检`，前端取同一 `项` 的 `结论` 与 `发现` 数量，**只渲染不重判**（红线 25）。

### 3.4 时序（先后顺序是红线）

```
点击「保存并重渲染」
 1. POST /api/hub/asset {task_id, n, desc, expect_desc}
 2. 服务端持 task_lock → 状态守卫 → 幂等检查（同值 → unchanged，不重渲染）
 3. 写清单第 8 列（组内行整组写）→ 回读该行真值
 4. 状态=awaiting_assets → 直接返回（重渲染=false，文案「确认置换时生效」）
 5. 状态=awaiting_approval →
    5.1 fetch_prompt(bridge_id, audio_mode)     ← 与 do_render 同一处 bridge GET
    5.2 正文校验（<200 字拒）
    5.3 tmp 写 + os.replace → 提示词.md          ← 原子替换，不留半截正文
    5.4 重算 approval_snapshot                   ← 正文变了不算=之后 approve 永远对不上
    5.5 run_selfcheck → 落 自检.json             ← 读的就是刚落的这一代正文
    5.6 run_audio_gate → 落 audio_gate
 6. 释放锁 → 200 回显 {我的描述, 重渲染, 自检, prompt_md, audio_gate, state}
 7. 前端用响应直接替换 detail 的这三块（不等 5s 轮询）；随后 onRefresh() 刷列表
```

**红线**：必须「先重渲染、后自检」。反序会把旧正文判一遍，产出假 PASS/假 FAIL；`自检.json` 与 `提示词.md` 永远是同一代。

### 3.5 失败矩阵（失败回滚的真实语义）

写清单与重渲染**不是同一个事务**。顺序固定「先写、后渲染」，且渲染失败**不回滚清单**（用户的输入是资产，不能丢）；要保证的是「提示词/快照/自检三者仍是同一代」——渲染失败时一个字节都不落盘。

| 失败点 | 磁盘结果 | 用户看到 | 可否重试 |
|---|---|---|---|
| 状态不符 | 零改动 | 409 原文（点名现状 + 真实出口） | 按钮应已置灰 |
| 期望现值冲突（别处改过同一行） | 零改动 | 409「这一行刚被别处改过（现为：…）」+ 两个选择：「用最新的」「保留我的输入」 | 是 |
| 清单写失败（行不存在/文件坏） | 零改动 | 500「保存失败：<原文>；清单未改」 | 是 |
| 取正文失败 / 正文过短 | **清单已改**；提示词/快照/自检仍是上一代 | 500「描述已保存，但重渲染失败：<原文>」+「再试一次重渲染」 | 是（重试只重渲染，不再写清单） |
| 自检器自身异常 | 提示词新一代；`自检.json` 落 FAIL 记录（既有兜底 `selfcheck.py:129-134`） | 200，面板显「自检没跑起来（检查器自己异常了）」 | 是 |
| 网络断 / 前端崩 | **未知**（可能已写并已重渲染） | 「结果未知，点「刷新详情」核对」+ 自动 reload | 刷新后按 GET 对齐 |
| 音频门禁重跑失败 | 提示词与自检已落，门禁结果空 | 门禁条按既有「未跑」形态显示（不伪造 PASS） | 是 |

设计要点：网络类失败**不许**显示"保存失败"（会诱发重复提交）；只有拿到 4xx/5xx 明确响应才断言失败。

### 3.6 并发编辑与重复提交

| 场景 | 处理 |
|---|---|
| 服务端并发 | 与 `set_asset` / `confirm` / `rollback` / `set_audio_mode` **同一把** `task_lock`（`hub_api.task_lock`）；重渲染在锁内，不会与退回置换/确认置换交叉 |
| 同卡多写 | 新增 `BusyKind = "desc"`；保存期间该卡其它写动作（传图/移除/合并）一并置灰（沿用既有 `busy !== null` 写法） |
| 重复提交 | 前端按钮 loading；服务端幂等：`desc == 现值` → `{unchanged:true}`，不写不渲染（连点两次只产生一代提示词） |
| 5s 轮询 vs 草稿 | 轮询**不覆盖** dirty 草稿；非 dirty 时按服务端回填；dirty 且服务端值变化 → 行内提示「这一行刚被别处改过」并给两个选择（不静默覆盖用户输入） |
| 多窗口 / 磁盘兜底改 | `expect_desc`（乐观锁）→ 409，禁止丢失更新 |
| 同任务两个编辑器 | 行级互斥：同时只允许一个行内编辑块打开（切换时若有 dirty 先确认） |

### 3.7 兜底路径（唯一允许出现"磁盘"字样的地方，且只在本方案文档/运维手册）

1. **UI 兜底（首选）**：「退回置换」→ 待置换区资产卡「用我的描述」→「确认置换」→ 后台渲染 → 自检自动重跑。功能与主路等价，代价是多 1 次状态回退、3 次点击，且 `自检.json` 会被作废后重建。
2. **运维兜底（不进 UI）**：直接改清单第 8 列（`analysis/reverse/<bridge_id>/待确认清单.md`，UTF-8，`|` 与换行需按其转义口径编码）。**仅限开发/运维排障**，产品文案中出现即判红。

### 6.3 探针（新建一处，判据全部机械可判）

`automation/probe_at22_e3.py`（照 `probe_at17_b3` 的隔离实例写法，零花钱：不调模型、不跑 ffmpeg）：

1. **[写层]** `replace.set_row(desc=)` / `set_group_write(desc=)`：单行/整组写入后逐字回读；`& | \r \n` 往返恒等；其它列字节不变（SHA 对比）。
2. **[守卫]** 不可写态（`discussing`/`rendering`/`approved`/`generating`/`done`/`failed`）的写描述请求 → 409，文案点名状态与出口；`expect_desc` 不符 → 409 且文件 SHA 不变；`awaiting_assets` → 200 且**不**重渲染（`重渲染.做了=false`）。
3. **[闭环]** 隔离实例真跑：制造残留 FAIL → `POST /api/hub/asset {desc}` → 200 且响应带新 `自检`（该项 PASS）、`prompt_md` 已换、`state` 仍 `awaiting_approval`、`approval_snapshot` 已重算 → 再 `GET /api/hub/task`（5s 轮询同一条路）结论一致。
4. **[失败原子性]** 桥渲染置 500：清单已写、`提示词.md`/`自检.json` SHA 不变、错误体带"描述已保存"标记。
5. **[幂等]** 同值二次提交 → `unchanged`，提示词 SHA 不变。
