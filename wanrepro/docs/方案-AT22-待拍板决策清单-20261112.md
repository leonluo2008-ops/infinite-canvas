## 二、E1 判定精度：残留词表收词规则

### 2.1 问题一句话

`entity_noun_core()` 把实体名第一个分句**整段**当核心词，`_noun_grams()` 再切 2–3 字组，于是「从右下角入画的第一人称右手」被切成「右下角／下角入／角入画／第一人称」，把用户**合法保留的构图描述**判成原物残留。

### 2.2 证据

**代码位置（已复核，实现批次改的就是这三处）**

| 作用 | 位置 | 现状 |
|---|---|---|
| 核心词取法 | `pipeline/reverse/render.py:1218 entity_noun_core` | 命名优先 → 去 `A：` 前缀 → 去尾注/括号 → 取**第一个分句** → 只留汉字，**整段当核心词** |
| 2–3 字组 | `pipeline/reverse/render.py:1232 _noun_grams` | 对核心词所有 2 字与 3 字滑窗成组 |
| 自检②报词 | `automation/selfcheck.py:348 _check_residue` | `words = {core} ∪ 2–3 字组`，`len(w) ≥ 3`，全文子串匹配，每词报首处 |
| 清扫吃词 | `pipeline/reverse/render.py:1260 strip_core_residue` | 与自检②共用同一套词表 |

**实测数据（66 个可测历史任务重放自检②）**

| 口径 | 命中词条 | 真残留 | 误报 | 误报率 | 纯误报文件 |
|---|---|---|---|---|---|
| 全量 | 232 | 213 | **19** | **8.2%** | **3** |
| 默认模板 seedance-flow | 19 | 16 | 3 | 15.8% | 1 |
| 旧模板 lumi-4section | 213 | 197 | 16 | 7.5% | 2 |

- 语料：`analysis/reverse/` 下 172 个任务目录 → **66 个可测**（同时有清单+提示词）、93 个提示词文件、**34 个任务有绑图行（36 行）**；
- **纯误报文件 = `1-85`、`1-94`、`3`（auto-0066）**：这 3 个任务的自检 FAIL **完全由误报造成**，用户按指引改了也改不掉（正文本身是对的）；
- 任务级：34 个有绑图行的任务里 4 个出现误报（1-103／1-85／1-94／3）= **11.8%**；
- 19 条误报**全部**落在 5 类源结构，无第六类：动作/方位碎片 7、视角碎片 4、通用占位名 2、自身标签行 5、品类泛化词 1。

**真实文案样例（auto-0066 落盘 `自检.json`，逐字）**

```
结论: FAIL
证据: #6 的「右下角」残留于正文: …前景右手持@图片1自右下角入画，无剪切。2-4…；
      #6 的「角入画」…；#6 的「下角入」…
      ｜已传图行词表 3 行（#1→图1(5词)、#5→图1(9词)、#6→图1(12词)），正文 516 字
```

三处命中的词全部来自 `#6 道具：从右下角入画的第一人称右手`，而正文那句「前景右手持@图片1自右下角入画」是**借创意的构图描述**，按产品规则必须保留。

**附带发现（比"红字"更严重，必须知情）**：清扫器 `strip_core_residue()` 与自检②共用同一套词表，**会真的吃掉合法构图词**——用真实函数跑合成句：

| 原句 | 清扫后 |
|---|---|
| `前景右手自右下角入画@图片1，无剪切。` | `前景右手自@图片1，无剪切。`（**「右下角入画」被吃**） |

即「用户写对的句子」只要构图词恰好紧邻图号就会被削掉。**这条 E2/E3 修不了**，只能靠 E1 收词 + E4 兜底（口径见 §6.1 与 §5.7 Q1）。

### 2.3 方案选项

同一语料、同一扫描口径，只换收词规则：

| # | 规则候选 | 词条 | 真残留 | 误报 | 误报率 | 纯误报文件 | 取舍 |
|---|---|---|---|---|---|---|---|
| R0 | 现状（整段切 2–3 字组，≥3 字） | 232 | 213 | 19 | 8.2% | 3 | 基准 |
| R1 | 动作/方位/视角词先删再切 | 221 | 213 | 8 | 3.6% | 2 | 可行但不够 |
| R2 | R1 + 通用占位名不进表 | 219 | 213 | 6 | 2.7% | 0 | 纯误报文件清零 |
| **R3** | **R2 + 实体自身标签行豁免** | **214** | **213** | **1** | **0.5%** | **0** | ✅✅ **推荐** |
| A | kind 闸门（只对主体建表） | 219 | 212 | 7 | 3.2% | 2 | ❌ 漏清 1 条真残留 |
| B | 实物名词闸门（须含瓶/盒/袋…） | 201 | 199 | 2 | 1.0% | 0 | ❌ 漏清 **14 条**真残留 |
| C | R3 + B | 200 | 199 | 1 | 0.5% | 0 | ❌ 误报同 R3，多漏 14 条 |
| D | 只提高长度阈值（≥4 字） | 4 | 3 | 1 | 25.0% | 3 | ❌ 灾难：真残留 213→3 |

- **D 为什么崩**：正文写「深棕色矩形香水**瓶**」，实体名写「深棕色矩形香水**小物体**」，两者只靠 3 字组（「形香水」「璃香水」「香水瓶」）搭桥，阈值一抬桥断；
- **B 为什么不能要**：36 个绑图行里 **26 行（72%）**核心词含泛化占位词「小物体」，「须含实物名词」等于把主力场景整类放弃检测。

### 2.4 主代理推荐：做，按 R3（三处改动，全在「取词」一侧）

```
entity_noun_core(ent)                      # 不动
  → strip_action_words(core)               # 新增①：删动作/方位/视角词（枚举黑名单 ~45 条）
  → if core ∈ GENERIC_NAMES: return ""     # 新增②：通用占位名不建表（~13 条）
  → _noun_grams(core)                      # 不动
  → [w for w in words if len(w) >= 3]      # 不动
selfcheck._check_residue: 跳过实体自身标签行（`<命名>（<形态>）` 孤立定义行）  # 新增③
E4 白名单在「进表后、匹配前」再滤一次（唯一过滤点）
```

**必须守住的四条约束（写进 B0 合同）**：
1. **零漏清**：真残留 213 条必须继续全拦——这是验收红线，「误报变少」不算过；
2. **单一过滤点**：`render.strip_core_residue()` 与 `selfcheck._check_residue()` 必须共用同一个取词函数，不许出现两套口径；
3. **空表 ≠ 跳过检查**：词表为空的行不建表（不报也不吃）是正确语义，但证据要写「该行无可判词」而不是静默；
4. **黑名单只增不减**：新增一条词必须带一次 66 任务语料回归（本轮探针即基线）。

**反例验证（审计最关心的「实物名恰好含动作词」，推荐规则逐例实跑）**

| 实体核心词 | 现状词表 | R3 词表 | 结论 |
|---|---|---|---|
| 从右下角入画的第一人称右手 | 12 词 | **0 词** | 误报消失 ✅ |
| 入画式香水瓶 | 5 词 | 3 词 | **真残留仍拦** ✅ |
| 第一人称视角的黑色香水瓶 | 11 词 | 5 词 | 仍拦 ✅ |
| 前景右手握持的喷雾瓶 | 9 词 | 3 词 | 仍拦 ✅ |
| 缓慢推近的镜头 | 6 词 | 1 词 | 近乎空表（建议叠一条「含 的/之 且 ≤4 字不收」，本轮语料零影响） |

关键差别：**R3 是「删词」不是「整行跳过」**——混合名里的实物部分活着，纯动作名自然空表。

### 2.5 成本与风险

- **成本**：一个纯字符串函数 + 两张小词表（动作/方位/视角 ~45 条、通用名 ~13 条）+ 一处标签行判断；无模型调用、无新依赖、无 IO，性能可忽略；**不改自检四项框架**（次序/锁点/组绑定/门禁一律不动）。
- **残余风险**（都靠 E4 兜）：
  1. 黑名单覆盖不全（新词如「POV」「跟拍」「环绕运镜」「空镜转场」）→ 每出现一次就是一次假红；
  2. 品类泛化词撞拍摄手法句（本轮 1 条：「外包装」命中「焦点锁死在手持产品与外包装正面细节」）；
  3. **同品类同色灰区**（香水换香水）→ 原物描述词对用户新品也成立；
  4. 潜在群体误报面：26/36 绑图行核心词含「小物体」，一旦正文任意一句出现「小物体」，26 个任务同时误报（本轮只因它恰好只出现在 bridge 3 的标签行才没扩散）。

### 2.6 是否可逆

**高**。纯代码改动，无数据迁移、无历史文件重写；回滚 = 回退该函数与两张词表。唯一不可逆的是「黑名单会随使用变成谁都不敢改的魔法常量」——用约束 4（只增不减 + 必带回归）压住。

## 三、E2 呈现重构：一条说清 · 去重 · 术语人话化

### 3.1 问题一句话

一条 finding 在可见区被说了 3 遍（结论人话 → 原因 → 发现逐条），第 4 遍在折叠区（证据）；行号重复 3 次、图号重复 4 次；用户看到的是**字段值**而不是话。

### 3.2 证据

**重复机制（auto-0066 真实 item 计数）**

| 同一信息 | 出现次数 | 位置 |
|---|---|---|
| 命中句 `…前景右手持@图片1自右下角入画，无剪切。2-4…` | **4 次** | 结论（间接）／原因／发现①～③／原始证据 |
| 命中词（右下角/下角入/角入画） | 3 条 × 2 处 = 6 处 | 发现列表 3 行 ＋ 原因串 3 段 |
| 行号 `6` | 3 次 | 结论「涉及行 #6」、发现前缀 `#6`、每条文字内 `#6 的…` |
| 图号 `1` | 4 次 | 发现前缀 `图1`、`@图片1`（2 处）、词表串 `#6→图1` |

根因在生产者侧（已复核）：`说明.原因 = _evidence(problems)`（`selfcheck.py:343/383/435/493`），而 `_evidence` 就是把每条发现文字用「；」拼成一段——**100% 重复**；`证据` 前半段又是同一段拼接。

### 3.3 方案选项

| 选项 | 做法 | 结论 |
|---|---|---|
| 现状 | 原因=发现拼接、统计直出可见区 | 用户读不懂（本次诉求） |
| **推荐** | 生产者产 finding v2 结构化字段；可见区一条只说一次；`原因` v2 不再产出；统计/键值/检查器原文全进折叠区 5 块 | ✅ 前端零字符串解析，只按槽位渲染 |
| 备选 B | 连折叠区也去重（删「检查器原始输出」块） | 可行但要迁 3 个探针断言，成本约半天、4 个文件；**默认不采**，理由见 §4.7 |

### 3.4 主代理推荐

**做。** finding v2 字段（生产者产、前端逐字渲染，一词一条）：

`行号 / 行称呼（短名，与置换卡同源）/ 类别 / 组 / 图号 / 图称呼 / 图引用 / 词 / 句序 / 上下文 / 片段[] / 原文 / 可修`

配套硬规则 4 条：
1. 可见区一条 finding 只说一次；同一行同一句的多个词在**渲染层**按 `行号+句序` 并成一张卡（数据层仍一词一条，供 E4 逐词保留）；
2. `#N` → 「第 N 行「短名」」；`图M`/`@图片M` → 「你传的产品图」＋缩略图（提示词原文引用处不改字）；
3. 一切统计（词表行数、正文字数、绿项/缺项、轮次、行→图号）只允许出现在折叠区；
4. 文案全部由生产者产出（红线 25），前端只按槽位渲染，不解析 `证据` 字符串、不拼业务话术。

配套产出：`项显示名`（绑图行残留→「提示词里的老词」等 5 条）、28 条术语对照表、可见区禁用正则（`#\d`、`图\d+`、`已传图行词表`、`必换行`、`analysis/reverse`、《原因：》…）。

### 3.5 成本与风险

- **成本**：`selfcheck.py` 文案/结构层改造 + `hub-api.ts` 类型 + `SelfCheckRow`/`GateBadge` 槽位重排 + 置换卡加两个锚点属性 + 新增 `probe_at22_e2`；
- **必须同期改的探针**：`probe_at16_b2` **4 条**断言（依赖 `说明.原因` 与 `#12` 写法），清单在 E2 §10.2；其余探针因 `证据` 字段内容不变而保持绿；
- **风险**：① 短名解析失败 → 退化为「第 6 行」，不阻塞；② 渲染层分组后「处数」口径变（3 处 → 1 句 3 词）→ 结论按「句」计数、统计里同时给词数/句数，E1 收窄后自然归一；③ 折叠区内容变多（默认关闭）。

### 3.6 是否可逆

**高。** 只动文案与呈现层；`自检.json` 顶层仍是列表，`证据`/`项`/`结论` 三键语义不变 → 回滚 = 前端 `SelfCheckRow` 退回旧槽位（单文件、单 commit）。历史 `自检.json` **有意不迁移**（读层降级，老任务显示旧文案并标注「早于人话上线」）。

## 四、E3 UI 内闭环：改这一行的描述 → 重渲染 → 自检重跑

### 4.1 问题一句话

自检②FAIL 时，唯一的处理指引是「去清单 `analysis/reverse/<桥>/待确认清单.md` 改『用我的描述』列」——磁盘路径对 web 用户不可操作，且 hub 侧**根本没有写这一列的接口**。

### 4.2 证据

**代码级（已复核）**

| 事实 | 位置 | 说明 |
|---|---|---|
| 唯一把用户导向磁盘的文案 | `automation/selfcheck.py:73-77` 定义 + `:384` 调用 | `_how_prompt_word()` 自述「只能改清单『用我的描述』列」；全库除此一处外没有指向磁盘的文案 |
| 数据列 | 清单第 8 列（`cells[7]`） | 渲染器读：`render.py:1550/1556 decode_user_desc`；`Entity.shape` 优先取它 |
| 画布链可写 | `ui/server.py:370-372 set_checklist_desc` → `POST /api/desc/<id>` | 但**任务根是画布侧** |
| hub 链不可写 | `ui/hub_api.py:2346 set_asset` 只有 `image_url/clear/text/命名/decision` | **这才是「去磁盘改」的根因** |
| hub 读不到现值 | `automation/cards.py:508-531` 有「描述」（第 3 列），**没有**「我的描述」 | 前端无从预填 |
| 不能走 `rendering` 态 | `automation/state.py:35-37 _ORDER` + `:166-171` | `awaiting_approval → rendering` 是非法边；既有合法先例是 `generate.py:233 rerender_for_audio_mode`（原地重渲染、不迁状态） |

**用户代价（现状）**：为了消一条假红 → 退回置换（丢 `自检.json`）→ 手改 markdown → 确认置换 → 重渲染 → 自检重跑；**多次离页 + 磁盘操作**。
**目标代价**：**2 次点击 + 输入，0 次离页，0 次磁盘操作，接口往返 ≤3s**（本机 bridge 渲染为秒级）。

### 4.3 方案选项

| 选项 | 做法 | 结论 |
|---|---|---|
| 甲 | 只改文案，仍让用户退回置换 + 改磁盘 | 诉求原样未解，不可接受 |
| 乙 | 新开 `/row-desc` 端点 + 新编辑器 | 会复制任务锁/行号校验/组联动/pending 流水，违反红线 25 |
| **丙（推荐）** | 扩既有点：`POST /api/hub/asset` 增 `desc` + `expect_desc`；一次请求内「写清单第 8 列 → 重出提示词 → 重算审批快照 → 自检重跑 → 音频门禁重跑」并回显；前端共享一个编辑器组件 | ✅ 复用唯一写层与唯一重渲染骨架 |

### 4.4 主代理推荐

**做。** 主路：发现行内点「改这一行的描述」→ 就地编辑（不弹窗、不换页）→「保存并重渲染」→ 面板就地刷新。

- **不改状态机**：沿用 AT-17 B3 的原地重渲染先例，不新增非法边；
- **顺序是红线**：先重渲染、后自检（反序会把旧正文判一遍，产出假 PASS/假 FAIL；`自检.json` 与 `提示词.md` 永远同代）；
- **写层复用**：`automation.replace`（`fill_row/set_row/set_group_write` 增 `desc`，组内整组同写）；
- **重渲染复用一处**：`generate.rerender_for_audio_mode`（`:233-263`）抽成 `rerender_in_place`，调用点 1→2，落盘改 `tmp + os.replace`；
- **并发**：同一把 `task_lock` + 行级 busy + 幂等（同值 `unchanged`）+ `expect_desc` 乐观锁 409 + 5s 轮询不覆盖 dirty 草稿；
- **失败语义**：写清单与重渲染不是同一事务——渲染失败**不回滚清单**（用户输入是资产），但**一个字节都不落盘**（提示词/自检 SHA 不变），文案如实说「描述已保存，但重渲染失败」；
- **状态守卫**：`awaiting_assets` 只写不渲染（承诺「确认置换时生效」）；`awaiting_approval` 写+重渲+自检；`approved`/`generating`/`done`/`failed` 一律 409 并**点名真实出口**（撤销批准／重试／复用为新版本）；
- **出口清理**：删除唯一磁盘指引（P0）；音频门禁 CLI 措辞改 UI 动作（P1）；另 5 处暴露内部文件名/术语的文案改人话（P2）；制度约束「新文档禁止出现改磁盘文件步骤」（P0）。

### 4.5 成本与风险

- **成本（最大的一项）**：后端写层（`replace`）+ 读层（`cards` 补 `我的描述`、`replace.parse_rows` 补读 `cells[7]`）+ `set_asset` desc 分支 + `rerender_in_place` 抽取 + `encode_user_desc`（格式所有者一处）+ 前端共享编辑器三件套（`useSaveRerender`/`SaveRerenderBar`/`HubTextEditor`）+ 起态门 + 新探针 `probe_at22_e3` + **11 条 AC**；
- **风险**：
  1. **残留词表不含 `my_desc`**（`render.py:1218-1229` 取词只看命名/「模型看到什么」）→ 改描述能把原物词挤出正文，但**不缩小词表**，用户可能改几轮仍红 → 必须允许连续迭代 + E4 作为第二出口；
  2. 写清单成功/渲染失败 → 清单与提示词不同代 → 文案如实说、自检不删、快照不重算；
  3. `set_asset` 一职多能（图/命名/决策/描述）→ 参数互斥 + 若审计判职责过载，退路是拆 `/row-desc` 并说明复制代价；
  4. **双份描述编码器**（`ui/server.py:283-288` vs `render.py:1090-1093`）→ 本批只新增 render 侧编码器，画布链那份记技术债，探针先锁「hub 侧往返恒等」。

### 4.6 是否可逆

**中高。** 代码可整体回退（新端点参数是新分支、重渲染是既有骨架的抽取）；**用户已保存的描述不会丢**（清单第 8 列是既有列，画布链同源）。不可逆的部分是一个中间态：若渲染失败后回滚，会留下「清单已是新值、提示词是旧值」的代差，需要靠重试自愈或人工对齐——这已写进失败矩阵，不是静默。

## 五、E4 误报豁免白名单：行×词粒度的用户裁量

### 5.1 问题一句话

再好的口径也不可能零误报（同品类、复合实体名、中性词跨行），用户没有「我认为这个词合法」的最终裁量权，只能被假红卡死或学会无视红条。

### 5.2 证据

- **口径残余清单（E1 落地后仍收不干净的 5 类）**：同品类换同品类（香水换香水）、客户产品外观特征词与 grams 重叠（「双耳奖杯造型」）、动作-实物复合名（「入画式香水瓶」）、跨行共享中性词（「透明」「第一视角」）、命名位带客户字样的其它 kind；
- **自检 FAIL 当前不是批准门禁（已复核）**：`generate.py:354 do_approve` 只在 `:373-374` 判**音频门禁** FAIL 才拒批准，自检结论在前端只是红条，批准按钮不受影响。→ **E4 的定位是「让自检可信」，不是「解锁」**：用户一旦学会无视红条，真残留（香水瓶/包装类）就没人看了；
- **实测误报形态**：auto-0066/0067 `#6` 行 3 处假红（见 §2.2），正是 E4 要一键放掉的那类。

### 5.3 方案选项

| 层级候选 | 结论 | 否决理由 |
|---|---|---|
| 按任务（一词全局生效） | ✗ | 同一词在不同行可能一处合法一处是真残留 → 全域免检 |
| 按绑定图（图号作用域） | ✗ | 图号每次渲染重算（`assign_numbers`），重编号后会串到别的实体 |
| 按行免检 | ✗ | 卡验收明令禁止：豁免粒度不可粗到整行 |
| 按正文原句 | ✗ | 用户一改描述就失配；等价整行免检；还产生第二份真源 |
| **行 × 词（推荐）** | ✓ | 与 finding 粒度同构；E1 改口径后仍按「这次词表里有没有这个词」判定，不串行 |

### 5.4 主代理推荐

**做，粒度只到「行 × 词」：**

- **落盘**：`任务.json → selfcheck_whitelist`（v1，唯一键 = `(行, 词键)`，词键 = `NFKC + strip + casefold`）；`图号`/`上下文` 只作证据快照，**不参与判定**；
- **过滤点唯一**：`实体筛选 → core → 闭包(core ∪ 2–3 字组) → ≥3 字 → 豁免过滤 → 正文匹配 → 结论装配`；位置在「词表已成型、尚未与正文比对」处（进表前没有词可豁免，命中后再滤会让「证据条数」与「展示条数」分裂）；
- **不重渲染、只重跑自检**：豁免不改任何渲染输入；重渲染会重算审批快照，并把「加一条裁量」耦合到 bridge 可用性上（bridge 挂了就加不了白 = 正被误报卡死时最不该发生）；
- **写路径**：`POST/DELETE /api/hub/task/<id>/residue-exempt`（body `{行, 词}`，撤销全部 `{全部:true}`），`task_lock` 内 `state.load → 改 → state.save`，响应自带重跑后的自检束；
- **7 条服务端校验**（不静默）：行存在 / 词长 3–20 / **词键 ∈ 该行本次词表闭包** / 该行已绑图 / 单任务 ≤50 条 / 状态必须 `awaiting_approval` / 同键幂等；
- **防放大**：无「整行免检」字段、无任务级词；豁免 `core` 也只去掉一个匹配项（2–3 字组仍逐条判）；PASS 证据必写「已按你的裁量保留 N 词」；失效条目灰显不自动删；单任务 >5 条时 UI 追加「可能是口径没收拾干净，值得回头收」；
- **台账 5 态**：`生效` / `失效-正文无此词` / `失效-行没绑图` / `失效-行不存在` / `未参与-不在词表`；
- **UI**：与 E3 同一动作组（主「改这一行的描述」，次「保留这个词」，逐词一颗、右对齐）+ 面板尾部「已按你的裁量保留 N 个词」折叠条（可撤销、可全部撤销）。

### 5.5 成本与风险

- **成本**：判定层过滤 + 台账 + 证据话术（`_finding` 增可选 `count`，旧格式逐字不变）+ 1 个端点 + `get_task` 透出 + 前端按钮与面板 + 边界表 B1–B14 的用例；
- **风险（如实）**：
  1. **一次豁免会压掉该行的全部命中**（同词多处）→ 证据显式给「该词另有 N 处命中」+ 可撤销；
  2. 面板会长期残留少量死条目（不自动清理）；
  3. 阶段一**不碰渲染侧清扫**（`strip_core_residue`），「清扫吃掉合法词」这条**不在覆盖面内**（见 Q4.1）。

### 5.6 是否可逆

**高。** 代码回退后 `selfcheck_whitelist` 成为 `任务.json` 里的无害死字段（`state.load` 原样读出整个 dict、`save` 原样写回，已复核 `automation/state.py:49-64`），不阻塞任何既有链路；判定层过滤点撤掉即恢复旧口径。撤销单条/全部都是运行期动作，随时可做。

## 六、跨项耦合与依赖（拍板时必须一起看）

### 6.1 E1 与 E4 的职责边界（两个过滤点，顺序固定，不能合并）

```
E1 = 默认口径，作用在「取词」阶段（进表前删动作/方位/视角词、通用占位名不建表、标签行豁免）
      → 影响所有任务，靠实体名文本特征，不需要人参与
E4 = 个案裁量，作用在「词表成型后、正文匹配前」（按 行×词 过滤）
      → 只影响加了白的这一行这一个词，必须人点
```

- **顺序不可换**：E1 若放到匹配后，会让「证据条数」与「展示条数」分裂；E4 若放到进表前，那时还没有词可豁免；
- **E1 收词后 E4 条目会自然失效**（变成「未参与-不在词表」，无害、灰显、可批量清）——这是设计好的降级，不是 bug；
- **E4 不得变成 E1 的替代品**：靠三条硬约束——V3 只接受该行词表闭包里的词、单任务 ≤50、**E1 实现批次的实测报告必须统计「豁免需求量」**（跑误报样本集看还有多少词要靠白名单）。这条量化口径是判断「E1 口径是否到位」的唯一证据。

### 6.2 E2 呈现依赖 E3 的闭环动作口径

- E2 把动作位冻结在 finding 模板的第 ⑥ 槽（一行两颗：主「改这一行的描述」在左、次「保留这个词」在右），**位置、文案、粒度由 E2 定**；
- **行为归属 E3/E4**：`可修: {类型: "改描述"}` 这个声明键由 E3 的生产者（`_check_residue`）写入，**只有它到场时主按钮才出**；
- **E2 单独先落地的后果（必须知情）**：`awaiting_approval` 态页面不渲染置换区，所以 E2 的 ③b「去这一行」定位按钮在该态会**置灰并提示「先点『退回置换』」**——等 E3 落地后才换成行内编辑入口。即：**E2 先上不会让操作更好，只会让文案更好读**；「能操作」要等 E3。
- **同函数共写纪律**：`selfcheck.py` 的文案改造分属两卡——E3 只改「绑图行残留」的 `处理`（`HOW_DESC`）+ 新增 `可修`；结论人话/原因去重/统计归 E2。两卡同批落地时必须**合并成一次提交**，否则会先后覆改同一个函数。

### 6.3 E3 与 E4：同一动作组，但**不得合并端点**

| | E3 | E4 |
|---|---|---|
