# 方案：删除通道原子化 + Windows 占用处置（卡 t_4f779245）

日期：2026-11-12　仓：`E:/User/GitHub/infinite-canvas/wanrepro`　分支：`feat/automation`
基线 HEAD：`47b6bef`　被修文件：`ui/hub_api.py`（`delete_task` 及其下游）

## 1. 需求（一手件：卡 t_4f779245 正文 + 根卡 t_abc4e7bf 现场证据）

人工强制结束后立刻删除，**不许**出现「任务从 API 消失 + 目录残留在磁盘 + 墓碑没写」这种不可达状态。
允许两种结局：**整删成功**，或**明确可解释的 4xx 且一个字节没删**。保持「删除不杀进程」语义。

## 2. 根因（已实测，不是推断）

现场（auto-0061）：force-finish 后 discuss 子进程仍在写 `拆解日志.txt`；`POST .../delete` → 500；随后
`任务.json` 已消失、只剩两个日志、再删报「任务不存在」、墓碑无记录。

本机实测（`C:/Users/leon3/AppData/Local/hermes/cache/scratch/rename_probe.py`，子进程持有
`拆解日志.txt` 的追加句柄）：

| 动作 | 结果 |
|---|---|
| `shutil.rmtree(任务目录)` | `PermissionError WinError 32`，**先删掉了未占用的 `任务.json`**（边遍历边删、不回滚） |
| `os.rename(任务目录 → .trash/…)` | `PermissionError WinError 5`（目录内有任何打开句柄，Windows 拒绝改名） |
| 子进程退出后再删 / 再改名 | 均正常 |

两条推论决定了修法：

1. Windows 上**不存在**「目录内有打开文件时仍把整个目录原子搬走」的手段 —— 所以「先落墓碑再 rmtree、
   失败回滚」这条思路在本平台不可实现（rmtree 已经吃掉一部分文件，回滚不回来）。
2. 「改名能否成功」= **该目录当前是否可整删**的精确探针：改得动 ⇒ 没有占用 ⇒ 整删可行；改不动 ⇒
   一个字节都没动。因此把**改名当提交点**，就能得到「要么完整存在、要么完整消失」。

代码层根因：`ui/hub_api.py::delete_task` 把 `shutil.rmtree(task_dir)` 直接连到 HTTP 异常层——无预检、
无重试、无墓碑兜底，异常冒到 `server.dispatch` 的兜底分支变 500，任务半删、不可再管。

### D1 提交点 = 移入隔离箱（`TASKS_DIR/.trash/`）

`delete_task` 的破坏段改为（全部在 `task_lock` 内）：

1. （沿用，非破坏）状态机准入 / JOB 阻断闭包 / 确认名 / `resolve_uploads_video` / `exec_snapshot`；
2. ① **墓碑先行**：`_tombstones_append(id, run_id)`；写不成（`OSError`）⇒ `HubError 409`
   「删除中止：墓碑写入失败…任务目录未做任何删除」，**零删除**。理由：墓碑是「编号不复用 +
   执行体退场」的唯一持久锚，崩在「API 消失但墓碑没写」之间会让编号被摄取复用；
3. ② **提交点**：`with state._file_lock(task_dir): _move_to_trash(task_dir)`
   —— `os.rename` 到 `TASKS_DIR/.trash/<id>.<YYYYmmdd-HHMMSS>-<pid>-<rand6>/`，占用时退避重试
   3 次（0.1/0.3/0.6s，覆盖杀毒/索引服务的瞬时占用）；`state._file_lock` 等锁超时（5s）⇒
   `HubError 409`「执行体正在写盘」+ 回滚墓碑 + 零删除；
4. ③ 改名成功 ⇒ 任务从 API 原子消失（`.trash` 不匹配 `auto-*`，不进 `list_tasks` /
   `scan_lost_runs` / `_bridge_still_referenced` / `_uploads_video_shared` / ingest 编号分配）；
5. ④ 尽力清箱 `_rmtree_retry(trash_path)`；清不净 ⇒ 回执 `trash_pending=true` + `trash_path` +
   `trash_error`，残留**只存在于隔离箱**（永不半删在原位），由 D3 清扫器后继回收；
6. ⑤ `analysis/reverse/<bridge_id>` 与 `uploads/<片>` 删除各自 best-effort（`OSError` 登记
   `analysis_skip` / `uploads_video_skip`），不得再 500；
7. ⑥ 收尾：箱空则删箱（**409 路径同样要做**）。`.locks/<id>.lock` **不删**（审计 I3：删了再
   重建会绕过 msvcrt 互斥）；
8. ⑦ 改名失败（占用）⇒ 回滚墓碑 + 清空箱 + `HubError`（`status=409`）人话，**零删除**、任务
   仍可管、可重试：
   「删除中止（未做任何删除）：任务目录被正在运行的程序占用，整目录搬不走。被占用文件：拆解日志.txt
   （共 2 个）；执行体 pid=19728 的心跳仍新鲜（可能仍在运行）。稍后重试即可——执行体退场后占用
   自动释放，系统不会替你杀进程；若一直占用，等它跑完或退出后再删。」
   文案口径（审计 P1）：只报「哪个文件被占 + 心跳是否新鲜」，**不声称**谁持有句柄。

### D2 占用诊断（只在 D1 失败后跑，非破坏）

`_locked_entries(dir)`：对目录内文件做 rename-probe（改名 `xxx.lockprobe` 立即改回，最多 5 个）——
改名失败者即被占用者。仅用于人话消息与探针断言，不做任何删除；改名成功者原样恢复。

### D3 兜底清扫 `sweep_residue(apply=False)`

| 类别 | 判据 | 动作 |
|---|---|---|
| 隔离箱条目 | `.trash/<id>.*` ∧ mtime ≥ 60s | `_rmtree_retry`；删净后箱空则删箱 |
| 事故形态孤儿目录 | `auto-*/` ∧ 无 `任务.json` ∧ **无 `inbox/`** ∧ mtime ≥ 600s | `_rmtree_retry`；`tombstoned` 仅作标注 |

「无 `inbox/`」是审计 BLOCKING-2 的硬约束：`ingest._create_task` 先建 `inbox/` 再走
`bridge.upload_video`（网络上行）才写 `任务.json`，慢上行 > 600s 的目录与事故形态无法区分，
不加这条会误杀正在摄取的视频（且 inbox 视频正被读句柄持有 = 又一次 Windows 半删）。

逐条登记 `removed` / `pending`（含原因）/ `errors`；`apply=False` 只报不动。**apply 口径写死**：

- 启动即对账（`startup_reconcile_async` 的 `_run`）与 watchdog 每轮 → `apply=True`（都包在
  `try/except` 里，清扫失败只打 stderr，绝不影响对账与 HTTP 服务）；
- `POST /api/hub/maintenance/sweep-residue` → **默认 dry-run**，请求体 `{"apply":true}` 才动。

### D4 不动的部分（边界）

- 不杀进程：D1 只在改名不可行时拒绝删除，从不 `TerminateProcess`；
- `force_finish` 三半闭环、`_job_alive` / `_job_blocks_retry` 口径、付费提交闸：不改；
- 「failed-but-alive 删除优先」保留：执行体活着但**没有持有文件**（如已退场的僵尸 pid）时，
  改名照样成功 → 照删不误；只有「真占着文件」才 409。

### 已知未解决（登记，不在本卡）

- 执行体的日志句柄以 `FILE_SHARE_READ|FILE_SHARE_WRITE` 打开（Python `open` 默认），**不含
  `FILE_SHARE_DELETE`**，这是「活着就删不动」的物理原因。要用 ctypes `CreateFileW` 打开日志
  （或写盘前读墓碑 run_id 自行退场）才能把 409 窗口压到接近零，属独立待办。
