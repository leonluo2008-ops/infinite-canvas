## 批次数据模型（身份字段清单）

落点 `CanvasProject.workflowBatches: WorkflowBatchRecord[]`（与 P2 `workflowTemplate`、P4 `workflowInstances`
同一种显式扩展字段：随项目持久化 + 随 v3 导出同路；**不进节点 metadata**，不建第二份 JSON）。

```
WorkflowBatchRecord
├─ schemaVersion: 1
├─ batchId / templateId / title
├─ signature            # 批次身份摘要 = 模板 + 各成员「模板#序号#素材摘要」排序拼接
├─ createdAt / updatedAt
└─ members: WorkflowBatchMember[]
     ├─ instanceId / templateId / instanceIndex
     ├─ materials        # 素材组摘要（身份：这批用的哪组素材）
     │    ├─ sourceVideoStorageKey / sourceVideoTitle
     │    ├─ intentChars / assetCount / optionalSegments
     │    └─ digest         # 可复算；改意图/挂图即变
     ├─ nodes            # 节点骨架 id 表（身份：哪些节点属于本实例）
     │    ├─ all[]              # **现存**节点全集（已退役占位产物不在内）
     │    ├─ sourceVideo / lapian / assemblyConfig
     │    ├─ product            # 执行期回填的本次组装产物（G18 闭合物）
     │    ├─ retiredPlaceholders[]  # 模板占位产物（已删，留档对账）
     │    ├─ videoConfig / videoTarget
     │    └─ downstream[]
     ├─ hub: { localId, bridgeId, revisionDigest, approvalSnapshot?, boundAt? } | null
     └─ backend: { lapianTaskId, lapianJobId, videoTaskId?, videoProvider? }
```

**字段清单的红线（§5.3 判据）**：上面每个字段都只回答「谁是谁 / 哪个属于哪个」，
**没有任何字段回答「现在怎么样」**——成员记录里既没有 `status`，也没有 `state` / `approved` / `progress`；
审批真源在 hub，生成真源在节点 `metadata.status` + 后端任务（探针逐条断言：成员 JSON 里这几类键一个都不出现）。

## 派生规则表（`deriveInstanceStatus`，顺序即优先级）

| 规则 | 判据（全部现查） | 结论 | 备注 |
| --- | --- | --- | --- |
| **R1** | 任一后端任务 `failed` / 任一成员节点 `status=error` / hub `failed` | `failed` | 失败证据优先，不被上游 success 掩盖 |
| **R2** | 成员**必需**节点（骨架去掉已退役占位产物）在快照里缺 | `unknown` | 删掉占位产物属正常终态，故不算必需 |
| **R3** | 产物节点就位 + 终态后端成功（视频链：视频任务 `succeeded`；非视频链：产物 `success`） | `done` | **唯一完成判据**；已声明 `videoTaskId` 但查不到 → 仍判 `unknown` |
| **R4** | hub `awaiting_approval` | `awaiting_approval` | P4 正常终点；**组装 Config success 也不改判完成** |
| **R5** | hub `approved` | `approved` | 批了未开始生成 |
| **R6** | hub `generating/generated/...`；或 `approved` 且视频任务 `queued/running` | `generating` | 已批准后在出片 |
| **R7** | 任一成员节点 `status=loading`；或任一后端任务 `queued/running` | `running` | 含「Config success 但视频仍 running」 |
| **R8** | 产物就位且成功 + 未绑 hub + 无视频任务 | `assembled` | 画布侧完成（P4 `canvas_ready`） |
| **R9** | 骨架齐、无产物、无任务、无 hub | `pending` | 入册未起跑 |
| **R10** | 以上都不成立 | `unknown` | 兜底：证据不足一律不判成功 |

**B5 两条硬口径在代码里的落点**：

1. **Config 早 success ≠ 实例完成**：Config/组装节点 `status=success` 只说明文本组装跑完了，
   R3 要求**终态产物**成功（视频链要视频后端任务 `succeeded`）——探针矩阵①「Config success + 视频 running → 进行中」。
2. **Lapian 无通用 status**：拉片节点不参与成功判定，只看 `backend.lapianTaskId/jobId` 的后端任务；
   查不到时进 `missing`（拉低覆盖率）但不把已有下游产物的实例打回 unknown——下游产物本身就是「拉片跑完了」的硬证据。
3. **缺失/未知 ≠ 成功**：任务缺失、节点缺失、查询未全覆盖，一律 `unknown` / `missing`，绝不落到 `done`。

批次聚合视图（`deriveBatchStatus`）：

```
BatchStatusView = { batchId, templateId, total,
                    members: InstanceStatusView[],       # 各自状态 + 命中规则 + 缺失证据
                    counts: {pending,running,assembled,awaiting_approval,approved,generating,done,failed,unknown},
                    coverage: { complete, partialUnknownMembers[], missingEvidence[] },
                    outcome: "done" | "in_progress" | "failed" | "partial_unknown" }
```

`outcome` 顺序：任一失败 → `failed`；覆盖率不全 → `partial_unknown`；全 done → `done`；否则 `in_progress`。
**覆盖率不全时永不给 `done`**（探针：缺一个成员的节点 → 该成员 unknown、批次 `partial_unknown`）。

## 查询覆盖（吃掉 20/100 截断）

- 生产查询 `generation_get_status`（`agent-node-text.ts` `buildGenerationStatus`）是「一次调用一个截断列表」：
  `limit` 缺省 20、被夹在 1..100、`tasks.slice(0, limit)`，**无 offset/cursor**（B5）。
- `queryBatchMemberTasks` 的做法：成员节点 id 去重 → 按上限 100 分块 → 块内 `limit = 块大小`；
  用 `total > tasks.length` 判截断 → **二分重查**（既有接口无分页，缩小查询面是等价物）；
  `source:id` 本地去重；查不全的 id 进 `uncoveredNodeIds` + `complete=false` + 显式 warning「部分未知」。
- 探针实测（后端 = 生产函数）：39 个成员节点裸查 → `total=39 / 返回 20`（陷阱复现）；分组查询 → 全覆盖；
  构造 30 成员 / **390 个节点** 的规模 → 全覆盖 390/390，分多块下发，零静默截断。

## 落盘 flush（A8/G14）

- `canvas-persist-queue.ts`：`setItem` 只入队（合并到最新一份）；`flush()` 丢掉 400ms 防抖计时器立即写；
  写失败返回 `ok:false` + `onError`，**保留待写值**（下次 flush/防抖仍会重试），不静默丢数据。
- `use-canvas-store`：持久化改走该队列（载荷仍是 zustand 的 `{state, version}`——只存 `state` 会丢掉恢复所需的包装），
  暴露 `flushProjects(reason)` 与 `lastFlush {at, ok, bytes, reason, error?}`。
- 编排器 `runWorkflowInstance`：④′ 画布侧落库 → 入册 + `flush("instance_persisted")`；
  ⑤⑥ hub 绑定 + 身份/成员（含 hub 外键）→ `flush("awaiting_approval")`。
  `flush` 依赖可以回 `{ok:false}`（= `store.flushProjects` 的返回值）→ 记 `flushes[].ok=false` + warning，**实例不因此判失败**。
- 探针实测：防抖窗口内磁盘**不含**最新改动 → `flush` 后磁盘立即含；每条实例两次 flush 都 `ok && written`；
  写盘失败时 `flush.ok=false` + `lastFlush.error` + 编排器 warning 全可见。
