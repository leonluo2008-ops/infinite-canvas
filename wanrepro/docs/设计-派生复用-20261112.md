## 1. 背景与目标

### 1.1 所有者原始诉求（原文摘录）

> 成功生成视频后，若对第一次生成的视频不满意需要微调，目前没有办法做。需要一个「**复用**」功能：**复用之前拆解成功的成果，去编辑提示词或者替换某些资产，然后重新提交生成视频**。

### 1.2 现状为什么做不了

- 出片后任务停在 `done`：**没有任何前进一步的出边**（F2），唯一合法出边 `done→failed` 零调用点，且 failed 之后只能回 `discussing` 重走全程。
- 唯一近似能力是 `failed → discussing` 的「重试」：产物齐时不重跑模型，但它的落点是**回到 awaiting_assets 重走**（确认置换 → 重渲染 → 再批准），不是断点续跑，也不服务 `done`。
- `awaiting_approval` 态能原地改（退回置换、改三态重渲染、撤销批准改配置），但这些都发生在**本版出片之前**；出片之后的第二版没有载体。
- 提示词在 hub 侧**纯只读**（F11），没有任何编辑入口——"编辑提示词"当前根本没有 UI 承载。

### 1.3 与「多方案并行」项目目标的关系

「多方案并行」要求同一份素材能同时生长出多条互不干扰的方案、每条方案历史可追。当前结构是「一个视频=一个任务=一条线性流水线」，出片即封版，本质是**串行单版本**。本功能把「一条拆解成果」变成可复用的上游资产，让 N 个版本从同一条拆解并行生长——它是多方案并行最小可落地的第一步，也是后续（版本对比、批量出片）的地基。

### 1.4 本文目标

定 D1–D6 六项设计决策、V1 边界、影响面与验收场景，交所有者逐项拍板；**不写实现、不拆批次**。

## 2. 决策表（D1–D6）

> 每项格式：候选选项 → 主代理推荐 → 推荐理由 → 代价与风险 → 若不采纳推荐会怎样。

### D1 复用载体：派生新任务 vs 原任务回退重编辑

| 选项 | 做法 | 一句话 |
|---|---|---|
| **A（推荐）派生新任务** | 从 `done` 任务派生**新任务号**，继承拆解成果与配置，源任务一字不动 | 一版一任务、并行、可追 |
| B 原任务回退重编辑 | 给 `done` 开出边，原地改、原地重出 | 复用同一任务号，覆盖上一版 |
| C 克隆目录不建新号 | 复制目录再覆盖，任务号仍沿用原号 | 名字没变，内容变了 |

**主代理推荐：A 派生新任务。**

**推荐理由（正面论证）**

1. **状态机层，B 根本做不到**（不是"没写按钮"）：`done` 无前进一步出边；唯一合法出边 `done→failed` 零调用点，且 failed 唯一出口是 `discussing`（= 重走全程）。要 B 必须给 `done` 新开一条回边，等于破坏单向链不变量（F2）。
2. **多版本并行**：每个派生任务独立目录、独立状态、独立正文、独立快照、独立成片；A 版 `generating` 与 B 版 `awaiting_approval` 互不阻塞。B 方案下一个任务号只有一个状态机，第二版必然打断第一版。
3. **历史可追溯**：源任务的 `history`、`approval`（谁在何时批准了什么快照）、`成片.mp4`、`自检.json` 全部封版；派生任务从派生起点写自己的历史。B 会把这四条全部覆盖——"第一版长什么样、谁批的"永久丢失，`approval_snapshot` 只剩最后一版。
4. **审批与付费语义不被污染**：一次批准绑定一次提交一次扣费（F3/F8）。B 下同一任务号出现第二次批准、第二个 `cloud_task_id`，`approval` 被覆盖，对账与「未知收单」排查失去基线；A 下每版各自一份，天然对齐。
5. **失败/删除隔离**：派生版出片失败落自己的 `failed`，不动源成片；派生版可单独删除（`DELETABLE_STATES` 含 done），源任务独立可管理。B 下"回退后再失败"会把一个已成功交付的任务变成失败态。
6. **不动状态机不变量**：`done` 保持终态（F2），删除合同、清箱、对账、看板筛选零改动（§4）；且派生落 `awaiting_assets` 与现网「重试」落点完全一致（备忘 §1.3），用户不需学新概念。

**代价与风险**

- 任务条目变多、列表噪音增加（缓解：D4 双向链接 + 版本角标）。
- 磁盘占用增加：资产字节复制 + 成片各一份（单任务几十~上百 MB 量级，可接受）。
- 拆解产物必须**引用而非复制**（F17），否则每派生一版复制一套十层产物，浪费且必然漂移。
- 多任务共用 `bridge_id` 使 **bridge sidecar（清单/组/行决策）成为双方可写共享态**（F14）——D2 的隐性代价，必须显式决定（§8 Q2）。
- 派生入口若做成批量/无限派生会放大付费风险 → V1 不做批量（§3）。

**若不采纳推荐（走 B）**

- 必须新开 `done` 回边并重定义"终态"，推翻 F2/F3 全套不变量：删除合同、清箱扫描、存量对账、失败/完成判定、看板"已完成"语义逐个复核；
- 多版本并行直接不可能（一个任务号只有一个状态）；
- 历史只剩最后一版，出片追溯、扣费对账、"上一版为什么被换掉"全部无从回答；
- 与「多方案并行」方向相反，等于把要建的地基先挖掉。

### D2 继承范围：派生时带过去什么、绝不带什么

| 选项 | 范围 |
|---|---|
| **A（推荐）全继承 + 显式剥离** | 拆解产物/清单/代表帧（共享引用）、意图、资产字节（复制 + 引用串重写）、参数与三态；剥离生成历史/云端 id/审批痕迹/产物 |

**主代理推荐：A。** 继承/剥离按落点分四类（备忘 §4.1 字段级结论）：

| 类别 | 内容 | 落点 | 处理方式 |
|---|---|---|---|
| **共享引用（零复制）** | 十层拆解、`待确认清单.md/.json`、`资产清单.md`、代表帧 `看帧/`+`看帧.json`、`门禁.json`、`意图.txt`、`意图建议.md` | `analysis/reverse/<bridge_id>/`（F17） | 新任务写同一 `bridge_id` |

| **复制 + 重写** | 资产字节 → 新任务 `asset-uploads/`（sha1 内容寻址天然去重）；清单「资产图」列的 `local:<源号>/…` **改指新任务号** | F15/F16 | 只复制不重写 = 复制了也没被引用 |

**推荐理由**

- 「复用拆解成果」= 复用 F17 那份共享产物，它本来以 `bridge_id` 为键，引用是零成本；
- 资产字节是任务级私有（F15），`local:` 串内嵌任务号（F16），**跨任务引用会随源任务删除断链**（asset-uploads 无删除守卫）→ 必须复制；
- 剥离项是"这一次提交的一次性痕迹"，带过去会直接破坏审批与付费防线（F8：批准后正文/参数一变即 `approval_stale`）；且现成常量就是两条回退边的口径，复用可避免出现第三套清理规则。

**代价与风险**

- 共享 sidecar 是"双方可写"：派生任务改配对会改到源任务的清单可见内容（源任务已确认的提交图不受影响，因为提交读快照 F12；但源任务若还没确认，会看到被改过的清单）。
- 源任务 `asset-uploads` 无删除守卫（F16）→ 若选"跨任务引用不复制"，源任务被删就断链，因此推荐复制。
- 代表帧继承口径未逐行核实（备忘 §6-2）：`cards.py` + `frames.py` 需专项核对后才能承诺"零重抽"。
- 派生时点若资产已缺，必须如实标注，不静默沿用空壳。

**若不采纳推荐**

- 走 B：资产全部重传重配，用户真实痛点（"只换一个资产、改一句话"）几乎没被解决；
- 走 C：每次重拆，模型费与时长照付，与"复用拆解成果"字面冲突。

### D3 微调维度 V1 范围：「编辑提示词」到底走哪条路（显式引用红线 25）

**V1 只做两项**：① 替换资产；② 编辑提示词。模型/渠道切换**沿用既有重批能力**（F5），不新增。

#### D3-① 替换资产：走既有置换流，不新造

四个写入口（整批上传 / 逐卡定向写 / 逐卡行决策 / 成组解组）+ 确认置换原样可用（F13）。**边界事实**：提交只认 `assets_confirmed` 快照（F12），所以"换资产生效"只发生在 `awaiting_assets`——派生任务正好落在这一态。**不得承诺"在 done 任务上直接换图"**，那是快照合同的必然结果，不是缺陷。

#### D3-② 编辑提示词：模板参数重渲染 vs 渲染结果手改

| 路线 | 做法 | 能做到 | 做不到 |
|---|---|---|---|
| 甲 模板参数重渲染 | 复用 `rerender_for_audio_mode` 骨架（F9）：改参数 → 桥侧重渲染 → 重算快照 → 自检+门禁重跑 | 改 `audio_mode` 这类**枚举参数** | **改不了措辞**：渲染器唯一任务级参数是 `audio_mode`，正文来自十层拆解 + 模板（F7）；改文案必须改模板或改拆解产物，不是任务级微调 |
| **乙（推荐）渲染结果手改** | 直接编辑 `任务目录/提示词.md` → 重算快照 → 重跑自检 + 门禁（状态不变） | 任意改文案以适配换过的资产——正是所有者诉求 | 手改与再次模板重渲染会互相覆盖；措辞质量无自动门禁 |

**主代理推荐：乙「渲染结果手改」；编辑器需新建（备忘裁决），但只复用既有骨架与守卫，不新造技术路线。**

**推荐理由**

1. 所有者要的是改文案；甲只能调枚举参数，做不出这个动作（"看着省事但没解决诉求"）。
2. **数据上天然成立**：`do_approve` 带 config 时读**当前** `提示词.md` 现算 v2 快照（F8），所以「手改正文 → 批准」不会误判 `approval_stale`；提交侧同样按当前正文校验，批的与提的一致。手改发生在 `awaiting_approval`、批准之前，是天然安全区；批准后再改会被"审批已作废"挡住——**不需要新造审批防线**。
3. **明确裁掉 override 文件方案**（备忘 §6-6）：引入 `提示词-override.md` 要改渲染读取顺序、破坏 `render.py` 的字节确定性合同（F7），代价高于收益。落点就是唯一的 `提示词.md`。
4. **红线 25 逐条落点**（原文口径：*hub 属画布二开，禁止复刻画布已有实现、擅自新增参数与路线，新增必须溯源画布引擎合同*；出处见 §8 Q7）：
   - **不可复用 `model-script-editor`**（备忘裁决）：它产出渠道 JS 适配脚本、落 `AiConfig.channels[].models[].script`，与 `提示词.md` 无交集；快照/自检/门禁三套守卫一个都不认识，硬塞等于绕开审批铁律（F10）。
   - **该复用的一**：`rerender_for_audio_mode` 那条「改 → 原地 → 状态不变 → 快照重算 → 自检+门禁重跑」的已落地骨架（F9）。
   - **该复用的二**：`PromptSection` 的只读正文展示（F11）——派生任务详情继续用它展示，只在其上加一个"编辑"入口。
   - **新增的只有**：一个正文写入口（保存 + 回写 + 触发收尾链），以及下面两个守卫。
   - 编辑器技术依赖走包内已有的 CodeMirror（`@uiw/react-codemirror` 已在依赖里，F10 同一依赖），**不引入新的编辑器技术路线**；骨架形态可参考 `model-script-editor` 的布局，但**不复用其插件脚本语义**。

**两个必须新增的守卫（现状均无，不得写成既有能力）**

| 守卫 | 现状 | 新增内容 |
|---|---|---|
| G1 手改后/批准前**重跑自检** | `run_selfcheck` 只在 `do_render:213` / `rerender:264` 跑；手改正文不触发任何复核，批准时也不跑（F20） | 保存正文后触发自检 + 音频门禁；批准前再复核一次，结论随 `get_task` 透出 |
| G2 自检 **FAIL 阻断** | 现状只拦音频门禁 FAIL（`generate.py:373-374`），自检仅展示（F20） | 是否阻断批准/提交是**产品决策**（§8 Q4）；若采纳，属新增守卫，需立项 |

**代价与风险**

- **覆盖冲突**：手改后若再走「退回置换」再渲染，手改正文会被模板重渲染覆盖。处理规则（§8 Q3）：派生任务手改后落 `prompt_edited_at`，再次渲染时 UI 必须明示"重渲染将丢弃手改"，不静默覆盖。
- **质量无评分**：措辞好坏只能人工把关——付费停点即闸门，不额外造质量评分（红线 25：不新增路线）。
- **编辑必须在派生任务上做**：done 任务的正文是已批准快照的证据，改了会污染历史（备忘 §5.3）。

**若不采纳推荐（走甲）**

- 所有者"编辑提示词"事实上无法交付，只能选三态类枚举，功能会被打回；
- 若为交付临时把段落文本做成渲染器参数，等于**给渲染器新增参数通道，直接违反红线 25**，并让模板/拆解/参数三处真源打架。

### D4 版本关系呈现

| 选项 | 做法 |
|---|---|
| **A（推荐）轻量双向链接** | 新任务持久化 `derived_from`；原任务"派生版本列表"由遍历反查**即时生成**，不落盘 |
| B 只在新任务挂来源 | 原任务看不到自己有哪些派生版本 |
| C 版本树/独立版本面板 | 新 UI 面 + 并排对比，超 V1 |

**主代理推荐：A。**

```jsonc
// 派生任务的 任务.json（持久化、不可变、唯一真源）
"derived_from": {
  "local_id": "auto-0066",          // 来源任务号
  "bridge_id": "3",                 // 与来源同一拆解
  "at": "2026-11-12T23:40:00+08:00",

}
```

- **不在原任务写 `derived_versions`**：双向落盘产生两处真源，派生任务被删后原任务留脏引用（删除合同是整目录改名，F16，不会回头清别人的字段）。
- 原任务侧列表由遍历 `projects/auto-*/任务.json` 反查 `derived_from.local_id` 聚合——**扫描反查已有先例**（`_bridge_still_referenced`，`hub_api.py:1266-1276`），成本可忽略。

**展示位置**

| 位置 | 内容 |
|---|---|
| 派生任务详情抽屉头部 | `复用自 auto-0066 · 2026-11-12 23:40 · 改动：资产/提示词`，可点跳来源 |
| 来源任务详情抽屉新增「派生版本（N）」段 | 每行：新版本号 · 派生时间 · 改动维度 · 当前状态 · 成片有无，可点跳转；无派生则整段不渲染 |
| 列表卡片（`task-card.tsx`） | 派生任务角标 `v2/v3`；来源任务显示"N 个派生版本" |

**代价与风险**：多层派生（v2 再派生）的序号口径需定（§8 Q8）；反查随任务数线性增长（现有 `list_tasks` 本就逐任务读，量级不变）。

**若不采纳推荐**：走 B → 所有者从原任务找不到"改过哪几版、哪版出了片"；走 C → V1 新增版本树 UI 面，与"复用现有卡片/抽屉"（红线 25）冲突，收益集中在第二阶段。

### D5 审批停点：付费铁律不变

| 选项 | 做法 |
|---|---|
| **A（推荐）派生任务同样停在 `awaiting_approval`，由所有者亲手批准才生成** | 与现有停点一字不变 |
| B 派生时自动批准/自动提交 | 省一次点击，风险极高 |
| C 派生任务免审批（视为"已有历史批准"） | 等同绕过付费停点 |

**主代理推荐：A。派生任务必须自己走一遍 `awaiting_assets → rendering → awaiting_approval → approved`。**

**实现如何保证（全部是既有机制，不新增防线）**

1. 派生时按 `SUBMIT_RUNTIME_KEYS` + `ROLLBACK_CLEARED_KEYS` 剥离（F19），派生任务出生即"零审批痕迹"。
2. 引擎守卫：无 `approval.snapshot_sha256` 不能进 `approved`；`approved` 只能从 `awaiting_approval` 进（F3）。
3. hub 守卫：`start_submit` 要求 `approved|generating`，否则拒绝「提交需 approved（先批准）」；`_submit_block_kind` 拦 active/dispatch/unknown。
4. 派生端点**不得**调用 `do_approve`/`start_submit`，不得写任何 `gen_*` 字段（实现期用探针断言）。

**验收如何保证（写进 §7）**

- 派生完成后立刻读 `任务.json`：`approval`、`approval_snapshot`、`cloud_task_id` 全部不存在；
- 对派生任务直接调 `POST /api/hub/submit/<新任务号>` → 必须拒绝「提交需 approved」，渠道侧零创建；
- 批准前 `GET /api/hub/task/<新任务号>` 的 `state` 必须停在 `awaiting_approval`。

**代价**：每版一次人工批准 = 每版一次人工成本（付费铁律的应有之义，不优化）。

**若不采纳推荐**：拆掉"一次批准一次扣费"的唯一人工闸门，所有审批/对账/未知收单防线失去意义。**此项仅作记录，无需讨论。**

| 选项 | 做法 |

**具体落点**

| 位置 | 形态 | 说明 |

| 详情抽屉 done 分支 | 主按钮「复用为新版本」 | 确认弹层（可复用 `task-delete-confirm.tsx` 的二键确认形态）：列继承项 / 剥离项 / "将产生新任务号，出片需重新批准付费" |

**代价与风险**：done 任务多一个按钮，误点成本低但弹层必须写清"新任务号 + 重新付费批准"，避免"以为点一下白嫖一版"。

**若不采纳推荐**

- 走 B：预演被大量派生，列表噪音 + 每份都要人工清；且用户会以为"预演也能派生"是免费复制；

## 7. 验收标准草案

**S1 主场景：从 done 派生 → 换一个资产 + 改提示词 → 待审批 → 批准 → 出片，源任务零改动**

| 步 | 操作 | 期望 |
|---|---|---|
| 1 | done 任务 auto-00XX →「复用为新版本」→ 确认弹层勾选继承 → 确认 | 返回 auto-00YY；`derived_from.local_id=auto-00XX`；`state=awaiting_assets`；**无** `approval*`/`cloud_task_id`/`dispatch`/`gen_job` |
| 2 | 记录源任务基线 | `成片.mp4`、`提示词.md`、`任务.json` SHA256 存证 |
| 3 | 派生任务换掉 1 个资产并确认置换 | `assets_confirmed` 指向新资产（`local:auto-00YY/...`）；自动渲染 → `awaiting_approval` |
| 4 | 打开提示词编辑器改一句 → 保存 | `提示词.md` 变更；`prompt_edited_at` 落盘；快照重算；自检 + 音频门禁重跑且结果可见（FAIL 如实显示） |
| 5 | 不批准，直接 submit | 拒绝「提交需 approved」，渠道侧零创建 |
| 6 | 所有者亲手「批准出片」 | `approved → generating → done`；新成片落新任务目录 |
| 7 | 复核源任务 | 三份 SHA256 与第 2 步一致；详情显示「派生版本（1）」可点跳 |
| 8 | 反向复核 | 新任务详情显示「复用自 auto-00XX」可点跳 |

判定：S1 全步通过 = V1 可交付演示；任一 FAIL 如实记录，不降级、不勾通。

**S2 防回归（必做）**

- 派生任务失败 → 源任务仍 `done`、成片可下载、审批记录不变；
- 派生任务被删除 → 源任务「派生版本」列表自动少一行（无脏引用）；
- 老任务（无 `derived_from`/`prompt_edited_at`）读面与现状完全一致（字段缺失零渲染、零报错）；
- 派生任务走「退回置换」时，手改正文的覆盖行为符合 §8 Q3 的裁决（UI 先提示）。
