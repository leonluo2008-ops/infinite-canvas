方案：`docs/方案-删除通道原子化-20261112.md`　被修文件：`ui/hub_api.py`、`ui/server.py`

## 1. 结论

缺陷已根治：**强制结束后立刻删除不再出现 500 与「任务从 API 消失但目录残留」**。删除只有两种结局，
且两种都有机器断言：

| 结局 | 触发条件 | 回执 | 磁盘 |
|---|---|---|---|
| 整删 | 目录当前无任何打开句柄 | `200` + `trash_pending=false` | 任务目录完整消失、墓碑在案、隔离箱清空并移除 |
| 拒删 | 目录内有打开句柄（执行体仍在写日志）或任务文件锁被占 | `409` + 人话 | **一个字节都没动**：目录逐文件完整、无墓碑、任务仍可管可重试 |

第三种（中间态）：改名成功但清箱失败 → `200` + `trash_pending=true` + `trash_path`：任务从 API 完整消失，
残留只存在于 `projects/.trash/`（`.trash` 不匹配 `auto-*`，不进列表/对账/编号分配），由清扫器回收。
**任何路径都不再出现「原位半删」**。

## 2. 根因（实测，不是推断）

现场（auto-0061）：`force-finish` 成功 → 立刻 `delete` → `500`；`任务.json` 已消失、只剩两个日志、
再删报「任务不存在」、墓碑无记录。

本机实测（子进程持有 `拆解日志.txt` 追加句柄，`cache/scratch/rename_probe.py`）：

| 动作 | 结果 |
|---|---|
| `shutil.rmtree(任务目录)` | `PermissionError WinError 32`，且**先删掉了未占用的 `任务.json`**（边遍历边删、不回滚）—— 这就是「API 消失 + 目录残留」的机制 |
| `os.rename(任务目录 → .trash/…)` | `PermissionError WinError 5`：Windows 只要目录内有打开句柄就拒绝整目录改名 |
| 句柄释放后再删/再改名 | 均正常 |

推论决定修法：Windows 上没有「目录被占用时仍原子搬走」的手段（所以「先落墓碑再 rmtree、失败回滚」
不可实现，rmtree 已吃掉部分文件），但**「改得动 == 当前可整删」是精确判据**。

## 3. 修法

- **D1 提交点 = 移入隔离箱**：`delete_task` 破坏段改为
  ① 墓碑先行（写不成 → 409 中止、零删除）→ ② `with state._file_lock(task_dir): os.rename(→ projects/.trash/<id>.<ts>-<pid>-<rand>)`
  （占用退避重试 3 次）→ ③ 成功即任务从 API 原子消失 → ④ `_rmtree_retry` 清箱（失败只报 `trash_pending`）
  → ⑤ analysis/uploads 各自 best-effort（`analysis_skip` / `uploads_video_skip`）→ ⑥ 箱空删箱；
  ⑦ 改名失败 → 回滚墓碑 + 清空箱 + `HubError 409` 人话（`_locked_entries` 诊断出被占用文件名 + 执行体 pid/心跳状态）。
- **D2 占用诊断**：`_locked_entries` rename-probe（改名即刻改回），只测到第一个被占文件即停，且**不动
  `任务.json` / `心跳.json`**（避免复位失败把任务从列表弄丢），复位带重试、失败如实写进消息。
- **D3 兜底清扫** `sweep_residue`：清 `.trash/` 条目（龄 ≥60s）+ 事故形态孤儿目录（无 `任务.json`、
  **无 `inbox/`**、龄 ≥600s；含 `inbox/` 的摄取中间态只上报不删）。挂载：启动对账 + watchdog（apply=True）、
  新端点 `POST /api/hub/maintenance/sweep-residue`（默认 dry-run）。
- 语义未变：**不杀进程**；`force_finish` 三半闭环、`_job_alive` 口径、付费提交链一概未动。

## 4. 审计与收敛

两轮独立审计（t1-audit / glm-5.3，均在实现会话之外）：

| 轮次 | 结论 | 处置 |
|---|---|---|
| 方案审计 | 2 BLOCKING：① 墓碑写在改名之后 → 崩窗里编号可被摄取复用、老执行体心跳污染同号新任务；② 孤儿清扫会误杀「摄取中」（`ingest._create_task` 先建 inbox、上行后才写 任务.json）。另 4 IMPL / 4 POLISH | 全部采纳：墓碑改**先行**+失败回滚；孤儿判据加「无 inbox/」+ apply 口径写死；`_file_lock` 包改名；不删 `.locks`；回执只增不改 |
| 实现审计 | **BLOCKING = 0**，3 IMPL-FIXABLE | 全部修并补断言：IMPL-1 源目录被别人删掉时不再误报「被占用」+ 回滚墓碑（改为幂等成功、保留墓碑）；IMPL-2 `_locked_entries` 只测到第一个被占文件、跳过 API 锚、复位重试+如实留痕；IMPL-3 墓碑文件损坏不再静默覆盖历史条目（写路径专用 loader，损坏即 409 中止）。POLISH：隔离箱条目龄 `utime` 重算、锁忙分支换文案、uploads 已不在记 `already_gone` |

## 7. 已知债（本卡登记，未做）

1. 执行体日志句柄以 `FILE_SHARE_READ|FILE_SHARE_WRITE` 打开（Python `open` 默认，不含
   `FILE_SHARE_DELETE`）——这是「活着的 discuss 一秒钟都删不动」的物理原因。要让「强制结束后立刻删」
   真正做到 200，需要执行体写日志时用 `FILE_SHARE_DELETE`（ctypes `CreateFileW`），或在写盘前读墓碑
   run_id 自行退场。**属语义/口径扩展，需所有者拍板，未动。**
2. `analysis/reverse/` 残留不自动清扫（见 §6 现场发现）。
3. 硬崩在「墓碑已写、改名前」会留下「墓碑在 + 任务在」的保守矛盾态（编号被占、任务仍可管）——方向安全，
   不处理。
