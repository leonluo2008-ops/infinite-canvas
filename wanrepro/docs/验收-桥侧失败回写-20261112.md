## 2. 改后的通道（职责边界与唯一写点）

```
analyze.py（桥侧，子进程）                      discuss.py（hub 侧，线程/CLI）
──────────────────────────────                 ─────────────────────────────────────────
阶段边界 → 进度.json                             轮询 /api/job ─┐
失败 → mark_failure(step, code)                 404 + 进度.json 失败 ─┤
        {"stage":"失败",                          done 但产物缺 ─┤
         "error":"<步骤>失败（退出码 N[；细节]）"}        超时 ─┴─→ _task_failure(原文/退出码)
        ↑ 不写 任务.json                                        │
stderr → ui/server.py::analyze_video                          ↓
        job.error = "analyze.py 退出 N：<stderr 尾部>"   _fail_task（**唯一写点**）
                                          ┌──────────────┴──────────────┐
                                   state 非 failed                state 已 failed
                                          │                             │
                       transition(→failed, note=原文,       原因相同 → 不动盘（幂等）
                         extra={failed_reason, failed_at,   原因为兜底句 + 现在有原文 → 只升原因
                         failed_evidence{trigger,exit_code}})  （不写 history、不刷新 failed_at）
                                          │
                                     任务.json（只 discuss.py 写）
```

三条口径：

1. **原文优先**：`failed_reason` 写桥侧原文（`job.error` 逐字，或进度.json 的结构化 error）；只有两者都空
   （#7）才用 AT-18 冻结文案 `state.fake_run_reason(cur)` 兜底，并在 `failed_evidence.fallback_text=true`
   留痕。本模块不新造第二套用户可见文案。
2. **同一次失败只一条迁移**：`_fail_task` 是 discuss 侧唯一写点，进程内串行（`_FAIL_LOCK`）+ 写盘前重读
   （与 `state.fail_orphan_task` 同纪律），已是 failed 且原因相同则不动盘。看门狗先按冻结文案判死、随后
   原文才到的场景，只改 `failed_reason`（+`reason_upgraded_from`），不写 history、不刷新 `failed_at`。
3. **不重复触发降级**：本卡只在 `run_discuss` **活着并把失败报出来**的路径里降级；hub 侧退出码文件那条链
   （并行卡 `t_8b462f10`）只在「执行体已不存在」时降级。二者互斥，且运行态 → failed 的自动降级入口仍然
   只有 `state.fail_orphan_task` 一个（本卡没加新的运行态降级入口，只补了「已 failed」的原因字段）。
