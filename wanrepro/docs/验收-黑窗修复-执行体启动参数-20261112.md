## 2. 根因（与卡面初判不同，实测修正）

卡面初判是「未传 `CREATE_NO_WINDOW` 且未重定向 stdout/stderr」。两处都不成立：

- **stdout/stderr 早已重定向**：42e3c11 就把子进程 stdio 合流到 `拆解子进程日志.txt`
  （`ui/hub_api.py` `_spawn_process` 里 `log = log_path.open("ab")` → `stdout=log, stderr=STDOUT`）。
  正因为它被重定向，黑窗里才**什么都没有**。
- **`CREATE_NO_WINDOW` 加在 `DETACHED_PROCESS` 旁边是无效的**：Win32 文档明说
  `CREATE_NO_WINDOW` 在被 `DETACHED_PROCESS` / `CREATE_NEW_CONSOLE` 组合时被忽略。
  实测同样证实：`DETACHED_PROCESS|CREATE_NEW_PROCESS_GROUP|CREATE_NO_WINDOW` 仍弹窗（§3.0 用例 B）。

真正的根因是 **`DETACHED_PROCESS` 本身**：它让 console 子进程处在「无控制台」状态，
Win11 的默认终端（Windows Terminal 接管新控制台会话）会为这种状态下启动的 console 应用
新开一个终端窗口（`CASCADIA_HOSTING_WINDOW_CLASS` + 内部 `PseudoConsoleWindow`）。
执行体输出已写文件，于是窗口全黑；关掉这个窗口 = 关掉它的 ConPTY = 执行体被带走，
与用户「关闭黑窗=杀执行体」的观察逐字吻合。

## 3. 实测证据

### 3.1 走真代码路径的 A/B（`_spawn_process`，临时任务根隔离）

方法：同一进程里改 `hub_api._DETACH_FLAGS` 再调 `hub_api._spawn_process`，子进程睡 5s；
期间每 60ms 对「全部可见顶层窗口」做集合差分（父自身窗口在基线里，差集=新弹窗）。

| 用例 | creationflags | 新增可见窗口 | job 终态 | 执行日志 |
|---|---|---|---|---|
| 旧参数 | `0x208` DETACHED\|NEW_GROUP | **2**（WT 窗口 + PseudoConsoleWindow） | done / 0 | `exec-body-up` |
| 新参数 | `0x8000200` NO_WINDOW\|NEW_GROUP | **0** | done / 0 | `exec-body-up` |

### 3.0 参数矩阵（独立探针，真 Popen + 真 ffmpeg 孙进程）

| creationflags | 子进程有控制台 | 新增可见窗口 |
|---|---|---|
| `DETACHED_PROCESS\|CREATE_NEW_PROCESS_GROUP`（旧） | 有（PseudoConsoleWindow） | 1 个终端窗口 |
| `...\|CREATE_NO_WINDOW` | 有（标志被忽略） | 1 个终端窗口 |
| `CREATE_NO_WINDOW\|CREATE_NEW_PROCESS_GROUP`（新） | 无 | **0** |

新参数下子进程再跑真 `ffmpeg -version` / `ffprobe -version` / 真抽帧（`capture_output=True`，
与 `automation/frames.py` 同形）→ 新增窗口仍为 0，三条命令 rc 全 0、stdout 正常收进管道。

### 3.2 进程分离不回归

父进程 `_spawn_process` 起执行体（睡 25s）后对自己 `taskkill /F`（等价崩溃/停服），
另一进程在父死之后每 1s 采样 8 次：`child_alive_samples` 全 true、`parent_alive=false`。

## 4. 改动说明（最小 diff，仅 `ui/hub_api.py`）

1. `_DETACH_FLAGS`（Windows 分支，第 588–606 行区段，定义在 601 行）：
   `subprocess.DETACHED_PROCESS | subprocess.CREATE_NEW_PROCESS_GROUP`
   → `subprocess.CREATE_NO_WINDOW | subprocess.CREATE_NEW_PROCESS_GROUP`。
   注释写死「为什么不能配 DETACHED_PROCESS」「CREATE_NO_WINDOW 在 DETACHED 下被忽略」，
   防止后人改回去。POSIX 分支（`start_new_session=True`）**未动**。
2. `_spawn_process` docstring 的写序第 2 行：`（DETACHED / start_new_session）`
   → `（Windows: CREATE_NO_WINDOW|CREATE_NEW_PROCESS_GROUP / POSIX: setsid）`，避免文档与实现漂移。
3. stdio 重定向、`_reap` 退出码回写、心跳三写、隔离守卫：**一行未改**。

## 5. 遗留风险

- 同一台机器上 `ui/server.py` 自身若由默认终端托管，重启/停服时终端窗口行为与本修复无关；
  仓库内其余子进程启动点（如 `ui/server.py::run_py` 的 `subprocess.run`）是否会在别的父进程形态下弹窗，
  由排查卡 t_6f55ca0c 覆盖，本卡未扩范围。
- 复现/验收命令依赖 Windows Terminal 默认终端设置；若把默认终端换回 conhost，
  `DETACHED_PROCESS` 的表现可能不同——但新参数（无控制台）在任何默认终端下都不会有窗口。
