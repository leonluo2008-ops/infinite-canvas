## 6. 进程分离语义（父死子活）

方法：`detach_parent.py` 用**真** `hub_api._spawn_process` 起执行体（`python -u -c` 每 0.5s 打点、共 40 次），
随即 `taskkill /F` 杀掉自己（等价 server 崩溃/停服）；独立守护进程 `detach_watchdog.py` 每 0.5s 采样父子存活。
隔离根为临时目录（不动真实 `automation/projects`）。

```json
{"parent_died_at_s": 3.5, "post_death_samples": 34,
 "post_death_alive_samples": 33, "all_alive_until_child_exit": true,
 "first_child_dead_at_s": 20.04, "child_alive_span_after_parent_death_s": 16.04}
```

子进程日志 `拆解子进程日志.txt` 尾部：`tick 35 … tick 39 / exec-body-done` —— 子进程把 40 次打点跑完
（40×0.5s=20s）后**自行正常退出**，不是被父进程带走的。父死后 16s 内 33 次采样全存活。

## 7. 遗留风险与后续建议

### 7.1 「执行体退出码.json」重试后仍是上一轮的凭证（既有缺陷，非本次回归）

- 现象：`start_retry` → 新 run 正常退出，`执行体退出码.json` 未更新，仍是上一轮 `52cc1ea14c6d`。
- 根因：`automation/state.py:938 exec_write` 的栅栏口径是「文件里已有退出码且 `run_id` ≠ 本次 run → 不覆盖」，
  于是**新 run 也被挡**；且 spawn/retry 时不清旧凭证。该行来自 `42e3c11`（git blame），**早于本次修复**。
- 影响：
  1. 诊断面误导——重试期间任务目录里挂着上一轮的死证（本轮实测：19:27–19:31 期间文件仍是 19:07:04 的 exit=3）；
  2. 启动对账的 E1（`exec_exit_written`）对**重试后**的 run 永不命中，死亡判定退化到 E2（`exec_pid_gone`）。
     本轮 `probe_at19_proc [3]` 证明 E2 路径同样立即生效，所以**不影响僵尸清理的正确性**，只影响证据类型与可读性。
- 建议：另开一张缺陷卡（单卡单根因）：栅栏应比对 `task.exec_run_id`（所有权），并在 `heartbeat_begin` 时清空/轮转旧凭证。
  **本卡按任务要求未改任何代码。**

### 7.2 其余

- 排查卡列出的 MCP stdio 层（中低）、PYTHONPATH 剥离（低潜伏）、JS `windowsHide`（低）均未在本链路触发，
  建议合并成一张「剩余子进程无窗口化」的低优卡，不阻塞本卡。
- 本轮验证期间仓库工作区存在**并行卡**的未提交改动（`automation/probe_discuss.py`、`pipeline/reverse/extract.py`）
  与并行探针写真实 `analysis/reverse`（`1-40-2` / `1-41-2`），已在 §3.1 说明；本卡未触碰这些文件/目录。
- 复现依赖 Win11 默认终端为 Windows Terminal：换回 conhost 时旧参数的表现可能不同，但新参数（无控制台）在任何默认终端下都不会有窗口。
